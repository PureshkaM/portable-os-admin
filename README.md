# portable-os-admin

Административное приложение для создания и администрирования переносной
операционной системы на внешнем LUKS-зашифрованном носителе — реализация
дипломного проекта.

Полное соответствие требованиям проекта и статус реализации —
в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Что делает приложение

- Хранит сведения о созданных переносных системах и данные восстановления
  в зашифрованном **контейнере администратора** (AES-256-GCM, ключ — через
  scrypt), доступном только в рамках **сеанса администратора**.
- Проверяет конфигурацию **штатным средством дистрибутива**: переводит её в
  kickstart (RedOS) или preseed (Debian/Astra) и отдаёт `ksvalidator` либо
  `debconf-set-selections --checkonly` — вдобавок к собственным структурным
  правилам.
- Создаёт, редактирует и проверяет **файл конфигурации установки**
  (аналог Kickstart-конфигурации): разметка носителя, параметры LUKS,
  учётная запись пользователя, удалённый доступ по SSH, список пакетов.
  На последнем шаге конфигурацию можно посмотреть и поправить целиком.
- Устанавливает ОС на внешний носитель **с локального установочного образа**
  (ISO), ничего не скачивая из интернета: размечает диск (EFI-раздел,
  незашифрованный `/boot`, LUKS-раздел, раздел логов, раздел обмена),
  создаёт LUKS2-раздел с пользовательским и recovery-keyslot'ом,
  разворачивает базовую систему через **debootstrap** (Debian/Ubuntu, Astra
  Linux) или **dnf --installroot** (RedOS/RHEL-совместимые) прямо с
  примонтированного образа, ставит ядро,
  initramfs с разблокировкой LUKS и загрузчик — так, чтобы носитель
  загружался на другой машине. BaseAlt/Alt Linux сознательно не
  поддерживается — см. `docs/ARCHITECTURE.md`.
- Позволяет подключиться к реальному репозиторию целевой ОС и выбрать
  пакеты для предустановки из фактического списка, а не набирать имена
  пакетов по памяти.
- Позволяет администратору просматривать журналы установленной ОС и
  обмениваться файлами с пользователем через отдельный раздел обмена.
- Выдаёт **код восстановления** по запросу от заблокированной переносной
  системы — без прямой передачи LUKS-пароля.

## Статус

**Установка на реальный носитель проверена сквозным прогоном (бэкенд
Debian).** На настоящей USB-флешке выполнен полный цикл: разметка диска →
LUKS2 с пользовательским и recovery-keyslot'ом → файловые системы →
`debootstrap` → ядро, initramfs и GRUB. Полученный носитель **загружается**:
UEFI → GRUB → ядро → запрос пароля LUKS → расшифрованный корень →
`multi-user.target`. Загрузившаяся система пишет журналы на незашифрованный
раздел, и они читаются штатным просмотрщиком без пароля пользователя.
Подробности прогона и список найденных при нём дефектов —
в `docs/ARCHITECTURE.md` "Сквозная проверка на реальном носителе".

Бэкенды **RedOS и Astra таким прогоном не проверялись** — их
kernel/bootloader-часть написана по конвенциям семейства и помечена в коде
как неподтверждённая. BaseAlt/Alt Linux сознательно не поддерживается.

Система для носителя берётся **только из локального образа**, который
администратор указывает при установке. Образы сетевой установки (netinst) не
подходят и отклоняются с объяснением: в них нет ядра и загрузчика. Пакеты
сверх базовой системы могут браться из репозитория организации или из сети.
Поддерживаемые сочетания «машина администратора × целевая ОС» и ограничения
по архитектуре — в `docs/ARCHITECTURE.md` «Поддерживаемые сочетания».

Программа запрашивает пароль привилегированного пользователя при запуске и
работает с правами root — она размечает диски и хранит контейнер
администратора. Перед установкой последний шаг показывает, что сейчас
находится на носителе (разделы, их размеры, файловые системы и метки), и
требует повторно ввести путь устройства: это последняя защита от установки не
на тот диск. Всё содержимое носителя при установке стирается безвозвратно.
См. `docs/ARCHITECTURE.md` "Известные ограничения" для точного статуса по
каждому бэкенду.

## Интерфейс

Графический (Tkinter), с пошаговыми мастерами: создание конфигурации и
установка ОС разбиты на шаги, каждый со своей проверкой, вместо одной большой
формы с ошибками после заполнения всего.

Текстовый интерфейс (Textual) был удалён: для задачи такой сложности им никто
не пользуется, а его удаление сделало `textual` ненужным — и вместе с ним
исчезла последняя зависимость, которую приходилось тянуть с PyPI.

## Требования

- Python 3.9+
- Для GUI — системный `tkinter` (пакет `python3-tk` на Debian/Ubuntu/Astra,
  `python3-tkinter` на RedOS/RHEL-семействе); при установке из `.deb`/`.rpm`
  подтягивается автоматически как системная зависимость.
- Для работы — Linux с правами root и утилитами `parted`, `cryptsetup`,
  `wipefs`, `sgdisk`, `mkfs.ext4`, `mkfs.vfat`, `debootstrap` и/или `dnf`.
  Их наличие проверяется до начала установки: недостающие перечисляются
  сразу, вместе с пакетами, которые их дают.
- Разработка и тесты возможны на любой Unix-системе (macOS/Linux) —
  деструктивные операции при этом просто не выполняются.

## Установка (разработка)

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e ".[dev]"
```

## Запуск

```bash
python3 -m portable_os_admin.gui.app
# или, если пакет установлен:
portable-os-admin
```

Права администратора запрашиваются через **polkit** — то же системное окно,
что и у прочих административных программ. Пароль вводится системе, а не этому
приложению.

При первом запуске приложение предложит создать новый контейнер
администратора (путь + пароль) либо открыть существующий.

## Тесты

```bash
pytest
```

110 тестов покрывают криптографию, контейнер администратора, сеанс,
конфигурацию и её валидацию, планирование разметки диска и команд LUKS (без
реального выполнения), фильтрацию списка устройств (включая приёмку
USB-накопителей с ненадёжным `RM`-битом), бэкенды установки
(Debian/RedOS/Astra), оркестратор установки, просмотр пакетов из реального
репозитория (с замоканной сетью), логику восстановления, запрос прав через
polkit и пользовательские сценарии в GUI (через headless `tk.Tk()`),
включая подтверждение перед стиранием
носителя, сортировку и множественный выбор пакетов, ручное редактирование
конфигурации и оба пошаговых мастера GUI.

Тесты **не** проверяют и не могут проверить, что установка на настоящий
носитель проходит успешно: это подтверждается только реальным прогоном на
железе. Поэтому тесты, которые просто перечисляли ожидаемые команды, убраны —
они проверяли реализацию против неё же. Оставлены те, что фиксируют
свойства, нарушение которых уже приводило к реальным дефектам: цепочка
«открыть LUKS → создать ФС → смонтировать → и только потом разворачивать
систему», обязательное освобождение всего смонтированного, адресация
`fstab`/`crypttab` по UUID, стирание старых разделов до смены таблицы.

## Структура проекта

```
src/portable_os_admin/
  crypto.py            # scrypt KDF, AES-GCM, генерация recovery-кода
  errors.py             # иерархия исключений
  session.py             # сеанс администратора
  container/            # контейнер администратора (шифрованное хранилище)
  config/               # файл конфигурации установки + валидация + repo_browser.py
  install/               # разметка диска, LUKS, образы, бэкенды ОС, оркестратор
    backends/            # debian (debootstrap), redos (dnf --installroot), astra
  recovery/              # запрос/выдача кода восстановления + recovery_module.sh
  admin/                 # просмотр журналов, раздел обмена, сопоставление носителя
  gui/                   # Tkinter-приложение: пошаговые мастера, запрос прав
tests/                    # pytest, 110 тестов
docs/ARCHITECTURE.md       # архитектура, трассировка требований, ограничения
packaging/                 # .deb (debian/) и .rpm (rpm/) для самого приложения
```
