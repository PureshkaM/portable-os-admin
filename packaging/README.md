# Упаковка приложения администратора (.deb / .rpm)

Приложение относится к системе «Якорь». Техническое имя пакета и команды
запуска сохраняется: `portable-os-admin`.

Собирает `portable-os-admin` в системный пакет для запуска прямо на
администраторской Linux-машине.

## Пакет ничего не скачивает при установке

Это требование, а не деталь: инструмент предназначен для контуров, у которых
нет выхода в интернет. Поэтому всё, что нужно приложению, — обычные пакеты
дистрибутива, объявленные в `Depends`/`Requires`, и ничего больше.

Так было не всегда. Прежняя версия создавала при установке приватный venv в
`/opt/portable-os-admin/venv` и ставила туда `textual` и `cryptography` **с
PyPI**, то есть требовала интернет в момент установки пакета. Причина была в
`textual`: в Debian bookworm он версии 0.1.13, до полного переписывания
библиотеки, и текстовый интерфейс на нём не работал.

Убрано целиком, двумя шагами:

1. **Текстовый интерфейс удалён** — им никто не пользуется для задач такой
   сложности. Вместе с ним исчезла и потребность в `textual`.
2. Единственной оставшейся сторонней библиотекой оказалась `cryptography`, а
   она есть штатным пакетом везде: `python3-cryptography` в Debian и
   RedOS. Нижняя граница версии в `pyproject.toml` — 2.6: `AESGCM` доступен
   с 2.0, `Scrypt` с 1.6, но обмен конфигурациями между администраторами
   подписывает посылку Ed25519 (`config/exchange.py`), а он появился только
   в 2.6 — граница считается по самому требовательному месту, а не по
   первому найденному.

Код теперь ставится как обычный системный Python-пакет
(`/usr/lib/python3/dist-packages` в `.deb`, `%{python3_sitelib}` в `.rpm`), а
`postinst`/`%post` не делают ничего. Проверено установкой через `dpkg -i`,
у которого нет сетевых возможностей в принципе.

## Права администратора — через polkit, а не своими руками

Приложение запрашивает права через `pkexec`, то есть показывает то же самое
системное окно, что и остальные административные программы рабочего стола.
Пароль вводится системе; приложение его не видит и никак не обрабатывает.

Пакет ставит три файла:

- `/usr/share/polkit-1/actions/ru.portableosadmin.policy` — описание действия,
  чтобы в окне было написано, что запрашивает права именно это приложение, а не
  безымянный `/usr/bin/env`;
- `/usr/share/polkit-1/rules.d/49-portable-os-admin.rules` — кто может это
  действие разрешить;
- `/usr/lib/portable-os-admin/launch-root` — запускатель, на который ссылается
  файл политики (polkit очищает окружение, поэтому переменные графического
  сеанса передаются ему аргументами).

Про правило стоит сказать отдельно, потому что это единственное место, где
пакет высказывается о политике машины. Debian объявляет администраторами
только `unix-group:sudo`. На системе, установленной с паролем root и без
sudo-пользователя, эта группа пуста — polkit тогда некого спросить и **не
показывает окна вообще**: программа просто отказывается запускаться, и у
администратора нет способа продолжить. Правило добавляет к списку `root` и
`wheel` (для RHEL-семейства) **только для действия этого приложения**; для
всего остального политика машины остаётся нетронутой.

На Debian в журнал polkit при этом попадает `Identity 'unix-group:wheel' is
not valid, ignoring` — группы `wheel` там нет, polkit её просто пропускает.
Запись безобидная и ожидаемая.

Агент, рисующий окно, приходит с рабочим столом, поэтому он в `Recommends`
списком альтернатив, а не в `Depends`: тянуть агент KDE на машину с GNOME
неправильно.

## Известные ограничения

- **Кросс-семейная установка не покрыта пакетными зависимостями.** `.deb`
  тянет `debootstrap` (нужен для целей Debian) в `Depends`, но не
  умеет тянуть `dnf` для целей RedOS с Debian-хоста (это часть базовой
  системы RHEL-семейства, а не отдельный пакет, который можно поставить на
  Debian). Симметрично: `.rpm` не объявляет `debootstrap` в `Requires`,
  потому что при исследовании репозиториев RedOS (`repo1.red-soft.ru`) он
  там не был найден.
- **BaseAlt/Alt Linux как цель установки не поддерживается вообще** — не
  найдено подтверждённого способа bootstrap'а с чужого хоста (см.
  «Архитектура» → «Известные ограничения» в README проекта).
- **`.rpm` не собирался и не проверялся.** `.deb` собран и установлен на
  реальной машине; спека правилась по тем же принципам, но `rpmbuild` на
  настоящем РЕД ОС в распоряжении не было. Раньше это компенсировалось
  запасным макросом `%{python3_sitelib}`, вычисленным из `sysconfig` того
  хоста, где идёт сборка, — и именно это оказалось дефектом: на Debian он
  указывал на `/usr/lib/python3/dist-packages`, путь, которого нет в
  `sys.path` интерпретатора РЕД ОС, так что собранный так `.rpm` ставился и
  падал `ModuleNotFoundError` при первом запуске. Запасного пути больше нет:
  `build-rpm.sh` при отсутствии настоящих RHEL-макросов (`python3-devel`)
  отказывается собирать вообще, а не отдаёт негодный пакет молча — то есть
  сейчас `.rpm` либо не собирается совсем (на любом хосте без
  `python3-devel`, включая Debian), либо собирается корректно на настоящем
  RHEL-семействе, но живой проверки последнего по-прежнему не было.
- Оба пакета помечены `Architecture: all`/`BuildArch: noarch` — собственного
  скомпилированного кода в них нет, а единственная платформенная зависимость
  (`cryptography`) приходит отдельным пакетом дистрибутива.

## Сборка

```sh
# на Debian/Ubuntu хосте
sudo apt-get install -y build-essential debhelper devscripts dh-python python3-all
./packaging/build-deb.sh

# на RedOS/RHEL-семейство хосте
sudo dnf install -y rpmdevtools rpm-build python3-devel
./packaging/build-rpm.sh
```

## Структура

```
packaging/
  debian/          # каноничные файлы для dpkg-buildpackage (build-deb.sh
                    # копирует их во временный ./debian на время сборки)
  polkit/          # действие, правило и запускатель для запроса прав
  rpm/
    portable-os-admin.spec
  build-deb.sh
  build-rpm.sh
```
