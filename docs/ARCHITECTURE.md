# Архитектура

Этот документ связывает курсовой проект («Проектирование защищённого
приложения для создания и администрирования переносной операционной системы
на внешнем носителе», КГУ, 2026) с фактической реализацией в этом
репозитории: какой модуль реализует какой класс/вариант использования из
документа, какие решения приняты при переходе от UML-моделей к рабочему
коду, и что осталось непроверенным или сознательно отложенным.

## Технологический стек

- **Python 3.9+**, без C-расширений, кроме `cryptography` (обёртка над
  OpenSSL/BoringSSL для AES-GCM и scrypt).
- **Textual** — TUI-библиотека для интерфейса администратора: три «окна» из
  курсового проекта (открытие/создание контейнера → главный экран → формы
  установки/логов/обмена/восстановления) реализованы как экраны (`Screen`) в
  одном Textual-приложении, а не как отдельные процессы — стек экранов
  (`push_screen`/`pop_screen`) даёт то же ощущение многооконности, что и
  Window flow в исходном WPF-варианте (см. соседний проект
  `WsusThirdPartyPublisher` в этом же рабочем каталоге, где такой подход уже
  применялся).
- **parted / cryptsetup / debootstrap / dnf / mkfs.\*** — внешние системные
  утилиты, вызываемые через `subprocess`, а не переизобретённые на Python.
- **Tkinter** — второй интерфейс, `gui/`, добавленный по обратной связи с
  первого реального теста на RedOS (см. «Обратная связь с первой реальной
  установки на RedOS» ниже): пошаговые мастера вместо одной формы. Работает
  поверх той же бизнес-логики, что и TUI; ничего в `container/`, `config/`,
  `install/`, `recovery/`, `admin/` ради него не менялось.

## Почему всё деструктивное — dry-run по умолчанию

Разработка велась в песочнице без доступа к запасным USB-накопителям и без
привилегий root на реальном Linux-хосте. Поэтому **любая** операция, которая
меняет содержимое диска (`parted`, `cryptsetup`, `mkfs.*`, `debootstrap`,
`dnf --installroot`, `mount`/`umount`), проходит через единственную точку —
`install/command_runner.py:CommandRunner.run()` — которая:

1. По умолчанию (`dry_run=True`) **не выполняет** команду, а только
   записывает её в `CommandPlan` для последующего анализа/логирования/теста.
2. Для реального выполнения (`dry_run=False`) требует **повторного**
   указания пути устройства в `confirm_device` — простая защита от случайного
   запуска установки не на том диске из-за опечатки в UI.

Это касается `DiskManager`, `LuksManager`, `OSInstaller`,
`LogViewer`/`ExchangeManager`.

**Обновление:** у пользователя появилась реальная Linux-машина (RedOS, с
полным доступом к зеркалам RedOS/Astra/BaseAlt) для тестирования настоящей
установки, поэтому `tui/screens/install.py` теперь предоставляет способ
включить `dry_run=False` — но не безусловно: экран добавляет отдельный
переключатель («Реальное выполнение») плюс обязательное повторное указание
пути устройства (`confirm_device`), и только когда оба совпадают, вызывается
`installer.run(..., dry_run=False, confirm_device=...)`. Это UI-level
подтверждение не заменяет проверку в `CommandRunner.run` — оно ровно то же
самое требование, просто явно показанное пользователю перед тем, как он
вообще нажмёт кнопку с реальным выполнением. Несмотря на то что путь теперь
доступен, статус "проверено на реальном железе" присваивается только по
факту подтверждённого пользователем успешного запуска — тот же принцип
честности, что и в `WsusThirdPartyPublisher`: «Treat any claim about runtime
behavior as unverified until the user confirms a real run».

## Сквозная проверка на реальном носителе (2026-08-20)

Пользователь дал доступ к тестовому контуру: виртуальная машина Debian 13
(trixie, arm64) в UTM на Apple Silicon с проброшенной внутрь настоящей
USB-флешкой. Это первый раз, когда код проекта выполнялся на настоящем
Linux с настоящим блочным устройством, а не в headless-песочнице, — и
проверка немедленно вскрыла, что **установка ОС не работала вообще**.

### Главный дефект: система ставилась мимо носителя

`OSInstaller.run()` форматировал LUKS-раздел, добавлял recovery-keyslot — и
на этом заканчивал работу с шифрованным томом. Контейнер **ни разу не
открывался** (`cryptsetup luksOpen`), на нём **не создавалась файловая
система**, он **никуда не монтировался**. Следом `debootstrap` запускался в
каталог `/mnt/poa-install-<id>`, который никто не создавал и который не имел
никакого отношения к флешке, — то есть базовая система разворачивалась в
обычную папку на диске машины администратора, а носитель оставался с пустым
зашифрованным разделом.

Ни один из 89 тестов этого не ловил: все они проверяли dry-run, где
`CommandRunner` только записывает команды в план, а «куда именно они
записывают данные» проверить в принципе невозможно. Регрессионный тест
`test_target_system_is_actually_written_onto_the_medium` теперь фиксирует
всю цепочку: `luksOpen` → `mkfs` на `/dev/mapper/...` → `mount` → и только
потом bootstrap в эту точку монтирования.

### Что ещё нашлось только на живом железе

1. **Проверка «носитель смонтирован» не срабатывала никогда.**
   `BlockDevice.mountpoints` заполнялся только точками монтирования самого
   диска, а десктопный автомонтировщик монтирует *разделы*
   (`/dev/sda1` → `/media/user/flash`). Проверка видела пустой список на
   любой реальной машине и пропускала разметку поверх живой ФС. Теперь
   `collect_mountpoints()` обходит всё поддерево `lsblk`, а установщик
   отмонтирует носитель сам — отдельным явным шагом в плане.
2. **Реальный запуск падал бы на первой же команде `cryptsetup`.**
   `LuksManager` создавал свой `CommandPlan(device=partition)`, то есть
   `/dev/sda2`, а `CommandRunner` сверяет `confirm_device` с `plan.device`.
   Пользователь подтверждает диск (`/dev/sda`), совпадения не было никогда.
   Менеджеры LUKS/диска теперь принимают общий план установщика.
3. **Носитель не мог загрузиться в принципе.** `/boot` находился внутри
   LUKS-тома, а GRUB не умеет открывать LUKS2 с KDF argon2id (его
   cryptodisk поддерживает только PBKDF2). Раскладка переделана — см.
   «Модель разметки диска».
4. **Ни ядра, ни initramfs, ни загрузчика.** `debootstrap` и
   `dnf install @core` дают базовую систему, а не загружаемую. Добавлен
   контракт `boot_packages` / `initramfs_command` / `bootloader_commands`.
5. **`config_files()` не вызывался ни разу** — `fstab` и `crypttab` не
   создавались вообще, при том что метод формально существовал.
6. **`chroot` без `/proc`, `/sys`, `/dev`** — `apt-get` внутри него
   неработоспособен.
7. **Учётная запись заблокирована (`passwd -l`), а автологина не было.**
   По замыслу LUKS-пароль — единственный секрет на входе, но загрузившись,
   пользователь упирался в приглашение входа, которое невозможно пройти.
8. **Таймаут команды 10 минут** — `debootstrap` на флешку в него не
   укладывается (реально занял ~55 минут).
9. **Ничего не освобождалось** — монтирования и LUKS-отображение
   оставались открытыми и при успехе, и при ошибке.
10. **Оба интерфейса подсовывали установщику выдуманное устройство.** И
    экран установки TUI, и мастер GUI собирали `BlockDevice` из
    собственных текстовых полей — с `model="(введено вручную)"` и
    `mountpoints=(None,)` — даже когда пользователь выбрал строку в
    автоопределённом списке. Это обнулило исправление №1: установщик
    отмонтирует носитель именно по `mountpoints`, а у выдуманного
    устройства их нет, так что разметка снова шла поверх живой ФС.
    Обнаружено уже после первого успешного прогона — по строчке
    `label='(введено вручную)'` в записи контейнера. Теперь оба
    интерфейса запрашивают реальное состояние устройства через
    `DeviceLister.describe()` и откатываются к полям формы только если
    прочитать его вообще не удалось.

### Чем подтверждено

Флешка 14,9 ГБ, Debian trixie arm64, установка `dry_run=False` целиком:

- разделы созданы на носителе: ESP 511M, `/boot` 1G, LUKS 10,9G, логи
  512M, обмен 2G;
- на ESP лежит `EFI/BOOT/BOOTAA64.EFI` (путь, который прошивка ищет на
  съёмном носителе) и каталог `poa/` с модулем восстановления;
- `/boot` содержит ядро `6.12.94+deb13-arm64`, initramfs и `grub.cfg` с
  верным `root=UUID=...`; в initramfs встроен `cryptroot/crypttab`;
- носитель **загружен** в эмулируемой UEFI-машине (`qemu-system-aarch64`,
  прошивка AAVMF): GRUB → ядро → initramfs → запрос пароля LUKS → корень
  расшифрован → `multi-user.target` без единого сбоя монтирования;
- загрузившаяся система записала журналы на **незашифрованный** раздел
  `POA_LOGS`, и `admin/logs.py:LogViewer` прочитал их оттуда (822 строки)
  без пароля пользователя — UC-5 подтверждён фактически;
- `find_media_by_boot_metadata` опознал носитель по метаданным ESP и нашёл
  соответствующую запись в контейнере администратора;
- отдельно прогнана установка **через мастер GUI**, а не через API: мастер
  сам подобрал проверенную конфигурацию, нашёл флешку в автосписке,
  подставил путь и размер, и выполнил реальную установку до конца
  (~62 минуты). Именно этот прогон и вскрыл дефект №10 ниже.

Бэкенды `redos` и `astra` этой проверки **не проходили** — их
kernel/bootloader-часть написана по конвенциям семейства и помечена в коде
как непроверенная.

## Обратная связь с первой реальной установки на RedOS (2026-07-31)

Первая попытка живого теста на RedOS-машине пользователя выявила три
проблемы, не видимые ни в каком headless-тесте:

1. **Реальная USB-флешка не появлялась в автоопределённом списке
   устройств.** Причина: `install/devices.py:DeviceLister` фильтровал строго
   по `lsblk`'s `RM` (removable) биту, а тот на практике часто равен `0` даже
   для явно съёмных накопителей (зависит от контроллера/переходника) — сам
   `lsblk` документирует `RM` как ненадёжный признак для многих реальных
   USB-устройств. **Исправлено**: теперь устройство также считается
   съёмным, если `lsblk`'s `TRAN` (транспорт) равен `usb`, даже при `RM=0`
   (см. `tests/test_devices.py::test_list_removable_accepts_usb_transport_even_when_rm_flag_is_wrong`).
2. **Просмотр пакетов из реального репозитория «ронял» интерфейс.**
   `PackageBrowserScreen`/`config_wizard`'s connect-handler выполняли
   `source.list_packages(...)` — сетевой запрос + разбор XML на десятки тысяч
   записей (RedOS: ~65 тыс. пакетов) — **синхронно в UI-потоке**. Для
   Textual это означало, что цикл перерисовки не мог отработать, пока запрос
   не завершится: экран выглядел зависшим/повреждённым на всё время
   загрузки. Список также молча обрезался до 200 строк без объяснения, что
   выглядело как «показывает не все пакеты». **Исправлено**: запрос
   вынесен в фоновый поток (`@work(thread=True)` в TUI,
   `gui.widgets.run_in_background` в GUI — оба маршалят результат обратно на
   UI-поток вместо прямой мутации виджетов из чужого потока), а обрезка
   списка теперь явно показывается пользователю с подсказкой уточнить
   фильтр.
3. **Пользователь счёл шаговую структуру TUI недостаточно понятной**: не
   было явного, невозможного пропустить шага «что вы вообще
   устанавливаете», а ошибки валидации показывались только после заполнения
   всей формы целиком, а не по мере ввода. По итогам явного решения
   пользователя добавлен второй интерфейс — `gui/` (см. ниже) — вместо
   доработки TUI, а не взамен него.

## Второй интерфейс: `gui/` (Tkinter, пошаговые мастера)

Добавлен после пункта 3 выше как отдельный, независимый presentation-слой
поверх той же бизнес-логики (`container/`, `config/`, `install/`,
`recovery/`, `admin/`) — ничего в этих пакетах не менялось ради GUI, поэтому
ничего в TUI не могло сломаться при его добавлении (обратное тоже верно).

- **Только стандартная библиотека** (`tkinter`), без Qt/новых pip-зависимостей
  — так `.deb`/`.rpm` из `packaging/` требуют только системный
  `python3-tk`/`python3-tkinter` (имена пакетов проверены напрямую по
  реальным индексам Debian bookworm и RedOS 8.0, не угаданы), без изменения
  общей схемы упаковки (venv для `textual`/`cryptography`, см. «Упаковка»
  ниже) — venv создаётся с `--system-site-packages`, чтобы видеть системный
  `tkinter`.
- **`gui/widgets.py:WizardFrame`** — общий каркас пошагового мастера: на
  каждом шаге проверяются (`validate_step`) только поля этого шага, а не
  всей формы разом — прямой ответ на пункт 3 выше. `MessageBar` заменяет
  Rich-разметку TUI (`[red]...[/red]`) на обычный текст с цветом. Каждый
  относительно долгий вызов (список устройств, просмотр репозитория,
  реальная установка) идёт через `run_in_background` — тот же принцип
  «не блокировать UI-поток», что и фикс пункта 2 выше.
- **`gui/screens/config_wizard.py`** — выбор целевой ОС является явным
  шагом 1 из 7 (радиокнопки Debian/RedOS/Astra с описанием), а не полем в
  общей форме — прямой ответ на пункт 3.
- **`gui/screens/install_wizard.py`** — шаг выбора носителя всегда
  показывает и автоопределённый список, и поле ручного ввода одновременно, с
  явным текстом «если носителя нет в списке — это нормально, введите путь
  вручную» — прямой ответ на пункт 1. Реальный запуск (`dry_run=False`)
  вызывает **тот же самый, не изменённый** `OSInstaller.run()`, что и TUI —
  этот мастер не трогает `install/installer.py`/`command_runner.py`, только
  переносит уже существующий блокирующий вызов в фоновый поток; кнопки
  навигации мастера блокируются на время выполнения, чтобы нельзя было
  разрушить фрейм с виджетами, пока реальная установка ещё идёт в фоне.
- **`portable-os-admin` теперь запускает GUI** (был TUI); TUI не удалён,
  доступен как `portable-os-admin-tui` — оба используют один и тот же
  `AdminSession`/`ContainerManager`/`ConfigManager`, так что контейнер и
  конфигурации, созданные в одном интерфейсе, полностью читаются в другом.
- 9 headless-тестов в `tests/test_gui.py` (реальный `tk.Tk()`, без дисплея —
  через `withdraw()`) покрывают то же самое, что `test_tui*.py`: полный
  мастер конфигурации, блокировку шага при некорректном имени пользователя,
  просмотр/добавление/удаление пакетов (с замоканным источником), dry-run
  установку, блокировку реальной установки при несовпадающем подтверждении
  устройства, удаление конфигурации.

| Специальная загрузочная среда / Recovery-модуль | `recovery/recovery_module.sh` (эталонная реализация, см. ограничения) |
| LUKS-раздел / Keyslot | `install/luks.py:LuksManager` (операции), сами keyslot'ы не моделируются отдельным классом — это состояние реального LUKS-заголовка |
| Просмотрщик журналов / Менеджер раздела обмена | `admin/logs.py:LogViewer`, `admin/exchange.py:ExchangeManager` |

## Модель разметки диска

`install/disk.py` реализует структуру разделов из §1.4.3 и диаграммы
развёртывания: `POA_ESP` (FAT32, EFI) → `POA_BOOT` (ext4) → `POA_SYSTEM`
(LUKS2, всё оставшееся место за вычетом двух следующих разделов) →
`POA_LOGS` (ext4) → `POA_EXCHANGE` (ext4).

**Почему `/boot` вынесен в отдельный незашифрованный раздел.** Изначально
разделов было четыре: ESP совмещал роль загрузочного раздела, а `/boot`
(ядро и initramfs) оказывался внутри LUKS-тома. Такой носитель не
загружается в принципе: чтобы прочитать ядро, GRUB должен сам открыть
LUKS-контейнер, а его модуль `cryptodisk` поддерживает в LUKS2 только KDF
PBKDF2 — конфигурация же по умолчанию (и требование §1.4.3) использует
argon2id. Пятый раздел решает это стандартным для зашифрованных установок
способом: GRUB и ядро читаются с открытого `POA_BOOT`, а пароль
запрашивает уже initramfs, один раз, по записи в `/etc/crypttab`. Никакие
пользовательские данные на `POA_BOOT` не попадают — только ядро,
initramfs и конфигурация загрузчика.

Разделы логов и
обмена — **обычные незашифрованные ext4-разделы вне LUKS-контейнера**, а не
часть системного раздела: это явно следует из диаграммы развёртывания
документа (§4.4, четыре отдельных раздела на носителе) и подтверждается
таблицей мер защиты §3, где для раздела обмена указано «доступ через
установленную систему», а не «шифрование». Это ключевое архитектурное
решение: оно позволяет `LogViewer`/`ExchangeManager` работать **без**
LUKS-пароля пользователя — администратор монтирует `POA_LOGS`/`POA_EXCHANGE`
напрямую.

## Идентификация носителя без раскрытия LUKS

Раздел `POA_ESP` содержит файл `poa/media_id.txt`, записанный при установке
(`OSInstaller._install_recovery_module`). `admin/media_lookup.py` читает
этот файл и сопоставляет `media_id` с `MediaRecord` в контейнере —
это реализация «Журналы.Носитель.Сопоставление» / «Обмен.Носитель.Сопоставление»
без необходимости открывать зашифрованный системный раздел.

## Схема кода восстановления

Требование «Восстановление.Код.НеПароль» реализовано буквально:

1. При установке генерируется случайный человекочитаемый `recovery_code`
   (`crypto.generate_recovery_code()`, формат `XXXX-XXXX-XXXX-XXXX`).
2. Реальная LUKS-парольная фраза recovery-keyslot'а —
   `scrypt(recovery_code, recovery_salt)` (`crypto.derive_recovery_passphrase`),
   **не** сам код.
3. В контейнере администратора хранится `recovery_code` (внутри
   зашифрованного контейнера) и `recovery_salt` — этого достаточно, чтобы
   выдать код администратору повторно предъявить пользователю, но сам код
   никогда не передаётся по сети и не виден вне контейнера/диалога
   администратор-пользователь.
4. Запрос восстановления — текстовая строка `media_id:slot:checksum`
   (`recovery/request.py:RecoveryRequest`), где `checksum` защищает от
   опечаток при устной/письменной передаче (УИ-7, «Запрос восстановления
   некорректен»).
5. Recovery-запись имеет только два состояния: `available` → `used`.
   Повторная выдача кода для одной и той же записи невозможна
   (`Восстановление.RecoveryЗапись.Недоступна`).

## Бэкенды установки ОС

Три поддерживаемых цели (`config.target_os`), реализующие общий
`install/backends/base.py:InstallBackend`:

| Цель | Bootstrap | Особенности, подтверждённые вживую |
| --- | --- | --- |
| `debian` (Debian/Ubuntu) | `debootstrap` | группа sudo — `sudo`, служба SSH — `ssh` |
| `redos` (RedOS) | `dnf --installroot` | группа sudo — `wheel`, служба SSH — `sshd`; репозитории/релизы/группа `@core` проверены напрямую по `repo1.red-soft.ru` (см. "Известные ограничения" ниже) |
| `astra` (Astra Linux) | `debootstrap` (наследует `DebianInstallBackend`) | группа sudo — `astra-admin` (**не** `sudo`); требует патченный Astra-специфичный пакет `debootstrap` на хосте-администраторе (suite-имена `orel`/`voronezh`/`smolensk` не распознаются апстримным debootstrap) |

BaseAlt/Alt Linux **не** реализован как цель установки — см. следующий
раздел.

## Просмотр пакетов из реального репозитория (`config/repo_browser.py`)

Чтобы не заставлять администратора набирать точные имена пакетов по памяти
при заполнении `config.packages`, `PackageBrowserScreen` (доступен из экрана
конфигураций кнопкой «Пакеты...») подключается напрямую к репозиторию цели
и показывает реальный список пакетов с версией/описанием:

- **`AptPackageSource`** (Debian, Astra) — читает apt-индекс
  `<mirror>/dists/<release>/main/binary-amd64/Packages.gz`. Проверено
  напрямую против `deb.debian.org/debian/dists/bookworm`.
- **`DnfPackageSource`** (RedOS) — читает `repodata/repomd.xml`, затем
  primary-метаданные. Проверено напрямую против
  `repo1.red-soft.ru/redos/8.0/x86_64/os`: метаданные там сжаты **zstd**
  (`*-primary.xml.zst`), не gzip, поэтому модуль вызывает системную утилиту
  `zstd` (тот же класс внешней зависимости, что `parted`/`cryptsetup` в
  остальном проекте) вместо добавления pip-зависимости `zstandard` ради
  одного этого запроса.

Оба источника — только HTTP GET по публичным метаданным, ничего
деструктивного не выполняется, поэтому этот модуль не проходит через
`CommandRunner`'овский dry-run gate.

## Упаковка (`packaging/`)

`.deb` (Debian/Ubuntu/Astra) и `.rpm` (RedOS/RHEL-семейство) для установки
самого приложения на администраторскую машину — подробности, включая
обоснование венва вместо системных Python-пакетов (системный
`python3-textual` в Debian bookworm — версии 0.1.13, до полного
переписывания библиотеки, несовместим с `textual>=0.58`, на котором
построен этот проект), в `packaging/README.md`. Ни один из пакетов не
собирался и не проверялся из песочницы разработки (нет `dpkg-buildpackage`/
`rpmbuild` на macOS) — сборка тоже часть цикла "собрать на реальной
машине → сообщить об ошибках".

Оба пакета теперь ставят два исполняемых файла — `portable-os-admin` (GUI,
по умолчанию) и `portable-os-admin-tui` (прежний TUI) — плюс
`.desktop`-файл для GUI в `/usr/share/applications/`. `python3-tk`
(`.deb`)/`python3-tkinter` (`.rpm`) добавлены в `Depends`/`Requires`: это
C-расширение, привязанное к системному Python, `pip` не может поставить
его в изолированный venv — оба имени пакетов проверены напрямую по
реальным индексам (`Packages.gz` Debian bookworm, `primary.xml` RedOS 8.0),
а не угаданы по конвенции. Поэтому `postinst`/`%post` теперь создают venv
с `python3 -m venv --system-site-packages`, чтобы он видел системный
`tkinter`, при этом `textual`/`cryptography` по-прежнему ставятся туда же
через `pip` поверх системных пакетов.

## Известные ограничения (сознательно отложено)

Аналогично рабочему соглашению в `WsusThirdPartyPublisher`, ниже — то, что
**не** стоит достраивать без явного запроса, и то, что помечено как
неподтверждённое до реального теста:

- **Интеграция recovery-скрипта с загрузчиком/initramfs не реализована.**
  `recovery/recovery_module.sh` — рабочий эталонный скрипт (реализует всю
  логику варианта использования УИ-9), но он не подключён к реальному
  GRUB/dracut/initramfs-tools хуку — это отдельная, сильно
  дистрибутив-специфичная инженерная задача. Скрипт также зависит от
  небандлящегося вспомогательного бинаря `poa-recovery-kdf` (scrypt на
  чистом POSIX sh нереализуем) — контракт его CLI описан прямо в скрипте.
- **`dry_run=False` подтверждён на реальном носителе — но только для
  бэкенда `debian`.** Полный цикл (разметка → LUKS → файловые системы →
  debootstrap → ядро/initramfs/GRUB → загрузка с запросом пароля) выполнен
  и проверен на настоящей USB-флешке, см. «Сквозная проверка на реальном
  носителе». Для `redos` и `astra` реальное выполнение по-прежнему
  **не проверялось**: их `boot_packages`/`bootloader_commands` написаны по
  конвенциям семейства (имена пакетов сверены с метаданными репозиториев,
  поведение `grub2-install`/`dracut` — нет). Оба интерфейса вызывают один и
  тот же, не продублированный `OSInstaller.run()`.
- **Установка в чужую архитектуру не поддерживается.** `InstallConfig.arch`
  существует, чтобы несовпадение было отвергнуто внятной ошибкой на входе,
  а не всплыло как «Exec format error» из `chroot` посреди установки:
  `debootstrap`/`dnf` наполняют корень чужой архитектуры только под
  `qemu-user-static`, и этот путь здесь не реализован. Проверка на реальном
  железе велась на arm64-хосте с arm64-целью; боевой сценарий (x86_64 хост,
  x86_64 цель) — такой же нативный случай.
- **RedOS: репозитории/релизы/группа `@core` проверены, GPG-ключ — нет.**
  Прямой проверкой `repo1.red-soft.ru` подтверждено: актуальные ветки —
  `7.3` и `8.0` (releasever — ровно эта строка), группа `@core` реально
  существует в comps.xml обеих веток, `openssh-server` обязателен в базовой
  группе. **Не подтверждено:** точное имя/путь GPG-ключа
  (`RPM-GPG-KEY-RED-SOFT` — не более чем правдоподобное предположение) —
  перед реальным запуском стоит свериться с `/etc/yum.repos.d/*.repo`
  `gpgkey=` прямо на тестовой машине, а не доверять этому файлу документации.
- **BaseAlt/Alt Linux сознательно не реализован как цель установки** (после
  явного решения пользователя отложить, а не строить на непроверенном
  механизме). Исследование не нашло документированного способа
  bootstrap'а корневой файловой системы Alt Linux с чужого хоста: штатный
  инструмент — `hasher` (`hasher-priv`), но он сам требует уже установленной
  apt-rpm/Alt-системы с привилегированным suid-хелпером — работающего
  аналога `debootstrap`/`dnf --installroot` для этого случая не
  задокументировано. Вернуться к этому стоит только когда появится реальный
  Alt Linux хост для проверки `hasher` напрямую, а не раньше.
- **Astra Linux: debootstrap-путь подтверждён, но с оговоркой.** Astra CE
  ("orel") — ребрендинг Debian 9; однако Astra распространяет собственный
  патченный пакет `debootstrap` (суффикс вида `astra7`) со скриптами для
  suite-имён `orel`/`voronezh`/`smolensk` — апстримный debootstrap эти имена
  может не распознать. Хосту-администратору нужен именно Astra-шный
  `debootstrap`, что этот проект установить не может (это должно быть уже
  на хосте). Также не подтверждено имя keyring-пакета для доверия
  Astra-репозиториям.
- **Диаграмма потоков данных / деревья опасностей / DREAD** из курсового
  проекта не переносились в код напрямую — они формировали требования
  (см. таблицу трассировки выше), а не отдельный программный артефакт.
- **Постоянный пароль ОС-уровня не назначается.** `useradd` создаёт учётную
  запись, но `passwd -l` сразу блокирует пароль — единственный секрет
  «переднего входа» в переносную систему это LUKS-пароль, заданный при
  установке. Это решение, а не недоработка: в документе нет отдельного
  варианта использования на смену OC-пароля пользователя, только LUKS-пароль
  и код восстановления. Следствие, обнаруженное при первой реальной
  загрузке: без пароля учётная запись непригодна и для входа, поэтому
  установщик кладёт drop-in автологина для `getty@tty1` — иначе разблокировка
  диска приводила бы к приглашению входа, которое невозможно пройти.
  Автологин настраивается только для первой виртуальной консоли; на
  последовательной консоли (`serial-getty`) входа не будет.
- **Категории апробации (STRIDE/DREAD) как автоматические проверки** —
  не реализованы как runtime-проверки; они были входом для решений
  (например, `Конфигурация.Использование.Запрет`), но нет отдельного
  «threat-model линтера» в коде.

## Локализация и UI

В отличие от `WsusThirdPartyPublisher`, этот проект **не** делает
русский/английский билингвизм первоклассной функцией — интерфейс и
сообщения на русском языке (как в исходном документе), без отдельного слоя
локализации. Это верно и для `gui/`, и для `tui/` — оба на русском, без
общего слоя строк между ними (небольшое дублирование текстов допущено
намеренно, а не по недосмотру, чтобы не создавать зависимость одного
интерфейса от другого). Если потребуется английский UI — стоит выделить
строки в отдельный модуль по образцу
`WsusThirdPartyPublisher/Localization/Strings.cs`, но это не делалось, так
как не запрашивалось.
