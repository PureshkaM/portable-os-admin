# Состояние проекта и рабочие заметки

Документ для того, кто продолжит работу — в том числе для меня же в следующей
сессии. `README.md` описывает, что программа делает, `docs/ARCHITECTURE.md` —
как она устроена и почему. Здесь третье: **где всё это проверялось, что
проверено, а что нет, и на чём тут можно обжечься.**

Актуально на 21 августа 2026, 191 тест.

---

## Коротко: где проект сейчас

Работающий инструмент, а не заготовка. Установка на реальную USB-флешку
выполнена целиком и полученный носитель **загружается** — это подтверждено
фактическим прогоном, а не тестами. До 20 августа 2026 проект не работал
вообще: он размечал носитель и разворачивал систему **мимо него**, в каталог на
диске машины администратора. Дефект прожил через 89 «зелёных» тестов и был
найден в первые же минуты работы с настоящим железом.

Отсюда главное правило проекта: **любое утверждение о поведении в runtime
считается непроверенным, пока не выполнено на живой машине.** Тесты доказывают,
что код согласуется сам с собой, и не более того.

## Тестовый контур

Это самая ценная часть обстановки — без неё проект возвращается в состояние
«пишем вслепую».

| Что | Где |
|---|---|
| Машина | ВМ Debian 13 (trixie, **arm64**) в UTM на Apple Silicon пользователя |
| Доступ | `ssh posvm` (алиас настроен), ключ `~/.ssh/portable_os_vm` |
| Адрес | `192.168.64.7`, вход root по ключу |
| Носитель | настоящая USB-флешка, проброшена в ВМ, `/dev/sda`, 14,9 ГБ, модель `OnlyDisk` |
| Образы | `/root/images/debian-13.6.0-amd64-DVD-1.iso`, `/root/images/redos-8.iso` |
| Рабочий стол | KDE Plasma на **Wayland**, пользователь `user`, `DISPLAY=:1` |
| Исходники в ВМ | `/root/portable-os-admin` (копия рабочего каталога с мака) |

**ВМ может быть выключена** — на момент написания этого файла она не отвечала.
Это нормально; её включает пользователь.

### Рабочий цикл

```sh
# правки делаются на маке, затем синхронизация в ВМ
rsync -az --delete --exclude '.git' --exclude '.venv' --exclude '__pycache__' \
      --exclude '.pytest_cache' --exclude '*.egg-info' \
      ~/ClaudeCode/portable-os-admin/ posvm:/root/portable-os-admin/

# тесты (venv не нужен — всё из системных пакетов)
ssh posvm 'cd /root/portable-os-admin && PYTHONPATH=src xvfb-run -a python3 -m pytest -q'

# сборка и установка пакета
ssh posvm 'rm -rf /root/poa-build && cp -r /root/portable-os-admin /root/poa-build \
  && cd /root/poa-build && sh packaging/build-deb.sh \
  && dpkg -i /root/portable-os-admin_0.1.0-1_all.deb'

# проверка загрузки готового носителя (эмулируемый UEFI, -snapshot, флешка не меняется)
ssh posvm '/root/boot-usb.sh /dev/sda'
```

### Как смотреть на GUI

Приложение можно поднять под `Xvfb` и снять скриншот — это единственный способ
увидеть интерфейс из сессии:

```sh
ssh posvm 'cd /root/portable-os-admin && PYTHONPATH=src \
  xvfb-run -a -s "-screen 0 1000x760x24" python3 -u /path/to/script.py'
# внутри скрипта: subprocess.run(["import", "-window", "root", "out.png"])
```

Скриншот затем забирается `scp` и читается как изображение. GUI-тесты работают
через настоящий `tk.Tk()` — реального дисплея не требуется.

## Грабли: на чём я обжёгся в этой сессии

Всё перечисленное произошло на самом деле.

1. **Я убил работающую установку пользователя.** Выполнил `pkill -f
   portable_os_admin` во время «уборки», не проверив, идёт ли работа.
   `debootstrap` осиротел и ещё девять минут писал на флешку впустую — её
   заметил пользователь по нагреву. **Никогда не убивать процессы по маске имени
   без проверки, что установка не идёт.**
2. **Не синхронизировать `rsync --delete` во время установки** — он заменяет
   исходники под работающим процессом.
3. **`widget.after()` из рабочего потока ломает Tkinter.** Это Tcl-вызов, а не
   потокобезопасная очередь. Симптом — `invalid command name ...poll` и
   молча теряющиеся события. Использовать `UiMailbox` из `gui/widgets.py`.
4. **Фоновый результат приходит в уничтоженный виджет.** Пользователь ушёл на
   другой шаг мастера — виджеты шага уже нет. Проверять `widget_alive()`.
5. **`importlib.resources.files()` из фонового потока роняет процесс.** Он
   тянет ленивый импорт и гонится с блокировкой импорта. Разрешать пути к
   ресурсам при импорте модуля, в главном потоке.
6. **`debconf-set-selections --checkonly` возвращает 0 на битом файле.** Вердикт
   брать из вывода, а не из кода возврата.
7. **`/usr/sbin` нет в `PATH` обычного пользователя**, а `sudo -E` передаёт
   именно его. Отсюда `[Errno 2] ... 'wipefs'` посреди установки. Пути к
   утилитам разрешаются явно в `install/tooling.py`.
8. **На установочном образе Debian нет подписи репозитория.** Есть
   `dists/<suite>/Release`, но нет ни `Release.gpg`, ни `InRelease`, поэтому
   `debootstrap` без `--no-check-gpg` падает на любом локальном образе. Дефект
   прожил незамеченным, потому что путь «установка с образа» ни разу не
   проходили целиком — ровно тот случай, о котором предупреждает первая
   строка этого файла.
9. **Не спешить объявлять дефектом непривычное имя пакета.** В RedOS 8 ядро
   называется `kernel-lt`, и `repoquery kernel` его не находит — но
   `kernel-lt` объявляет `Provides: kernel`, поэтому `dnf install kernel`
   разрешается штатно. Проверять разрешение зависимостей, а не совпадение имён.
10. **Сборщик мусора Python может уронить поток установки в вечное ожидание.**
    `tk.Variable` при уничтожении обращается к Tcl, а цикл сборки мусора
    запускается в том потоке, который первым исчерпал порог выделений. Значит,
    переменная, оставшаяся от закрытого экрана, может быть уничтожена **в
    потоке установки** — обращение к Tcl из чужого потока блокирует его
    навсегда. Наблюдалось буквально: поток стоял в `tkinter/__init__.py`
    `__del__`, окно при этом отвечало, установка не завершалась и не падала.
    Лечится сборкой мусора в главном потоке сразу после уничтожения виджетов
    (`show_frame`, `_render_step`) и перед запуском фоновой работы. Симптом
    легко принять за «тест подвисает» — это не тест.
11. **Установка с локального образа ломалась дважды, и оба раза — в местах,
    которых нет при установке из сети.** Первое: на образе нет подписи
    репозитория, `debootstrap` без `--no-check-gpg` не начинает работу.
    Второе: `debootstrap` записывает в устанавливаемую систему источник вида
    `file:///mnt/poa-image-<id>`, а внутри `chroot` этого пути нет — образ
    смонтирован снаружи. Внешне это выглядит как `Unable to locate package
    linux-image-amd64` через сорок минут после начала. Образ нужно
    подмонтировать внутрь целевого дерева **по тому же пути**. Третье, и оно
    же настоящая причина: `debootstrap` из `file://`-источника **оставляет
    `/etc/apt/sources.list` пустым** (для http-зеркала он его пишет, для
    file:// — нет), поэтому источники приходится писать самим, и с
    `[trusted=yes]`, потому что подписи на образе нет, а неподписанный
    репозиторий apt отбрасывает целиком. Общий вывод:
    прежний удачный прогон ничего не говорил об этом пути, потому что шёл из
    сети, где URL означает одно и то же по обе стороны chroot.
12. **Первый прогон тестов после синхронизации медленнее** — Python компилирует
   байт-код. Таймауты ожидания в тестах должны быть щедрыми.

## Открытый вопрос: память argon2id и переносимость

Замечено при загрузке готового носителя в эмулируемой машине с 2 ГБ памяти:

```
Warning: keyslot operation could fail as it requires more than available memory.
```

Стоимость argon2id **по памяти зашивается в заголовок LUKS при создании** и
подбирается `cryptsetup` под ту машину, где том создавался. Для обычного
диска это правильно, для **переносного** носителя — нет: сделанный на машине
с 32 ГБ носитель может потребовать при разблокировке больше памяти, чем есть
на машине, куда его принесли, и открыться медленно или не открыться вовсе.

Вариант решения: задавать `--pbkdf-memory` явным разумным потолком (например,
256 МиБ — для argon2id это по-прежнему стойко) либо вынести его в
конфигурацию. **Не реализовано, решение за пользователем.** Проверить просто:
собрать носитель и попробовать открыть его на машине с малым объёмом памяти.

## Где остановилось тестирование (21 августа 2026)

Загрузка носителя проверена до запроса пароля LUKS включительно. Дальше
проверялась реакция на **неверные** пароли: два отклонены штатно, третий
отправлялся, когда пользователь попросил свернуть тестирование. Поэтому
**срабатывание модуля восстановления после исчерпания попыток на живой
загрузке не подтверждено** — подтверждено лишь то, что он лежит внутри
initramfs и что хук упорядочен после `cryptroot`.

Чтобы продолжить: `sh boot-x86-screen.sh /dev/sda` (скрипт удалён при уборке,
но воспроизводится за минуту: qemu-system-x86_64, OVMF, `-snapshot`, сокет
монитора), затем три неверных пароля через `sendkey` и снимок экрана.

## Решения, которые не нужно пересматривать

Приняты пользователем явно. Если кажется, что стоит вернуть — сначала спросить.

- **Только GUI.** TUI (Textual) удалён; CLI не делать. Для задачи такой
  сложности ими не пользуются.
- **Никакого режима предпросмотра в интерфейсе.** Инструмент существует, чтобы
  ставить систему. `dry_run` остался параметром `OSInstaller` только ради
  тестов и наружу не выходит.
- **Система ставится с локального образа по умолчанию.** Контур может быть
  без выхода в интернет, поэтому образ — основной и рекомендованный путь.
  Установка из сетевого репозитория с 21.08.2026 снова возможна, но только
  как явный выбор: пустое поле образа плюс заданный в конфигурации адрес
  репозитория. Молча подменять образ сетью нельзя.
- **Netinstall-образы не подходят.** Отклоняются по существу: проверяется
  наличие ядра и загрузчика в индексе.
- **Путь к образу не хранится в конфигурации** — это параметр запуска.
- **Пакет самодостаточен**: никаких зависимостей с PyPI, никакого venv, всё из
  репозитория дистрибутива. Проверяется установкой через `dpkg -i`.
- **Права запрашиваются через polkit**, а не собственным окном ввода пароля.
- **Минимум зависимости от версий дистрибутивов.** Семейство, выпуск и
  архитектура читаются из образа; списков известных версий в коде нет.
- **Образ выбирается раньше конфигурации**, и конфигурации помечаются как
  подходящие или нет.
- **BaseAlt/Alt Linux не поддерживается** — не найдено способа bootstrap'а с
  чужого хоста.

## Что стоит помнить про общение

Пользователь проверяет утверждения и быстро замечает выдуманное. Работает это
хорошо: почти каждое его замечание указывало на настоящий дефект — мёртвая
опция VPN, поле `kdf`, которое никуда не передавалось, кнопки за краем экрана,
собственное окно пароля вместо polkit, скачивание системы из интернета. Стоит
воспринимать его замечания как отчёты об ошибках, а не как пожелания.

Отвечать фактами: если что-то не проверялось — так и говорить. Формулировка
«не проверено» здесь встречается часто и намеренно.
