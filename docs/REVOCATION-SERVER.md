# Сервер доступа и управления системы «Якорь»

С 15.11.2026 решение называется **«Якорь»**. Компоненты именуются по назначению: **приложение администратора**, **сервер доступа и управления**, **переносное устройство**, **корневой контейнер организации**.

Новый образ проверяет состояние носителя при загрузке, при подключении к сети
и раз в пять минут. После подписанного ответа `revoked` носитель закрывает
рабочую сеть, завершает клиент и VPN и сохраняет блокировку после перезагрузки.
Ключи и разделы остаются на месте. Для возвращённого носителя приложение
предлагает отдельную операцию локального стирания.

Сначала выведите старые тестовые образы из работы. Обновите сервер, затем
перевыпустите носители. У старого образа подписанный ответ `revoked` вызывал
стирание. Новый сервер отвечает на его запросы `/v2/state` кодом 403.
Такой отказ у старого образа сам по себе не прекращает уже открытый сеанс.
Новый образ использует только `/v3/media-state` и подписи новой версии.

После регистрации отзыва сервер отклоняет попытку вернуть прежней идентичности
состояние `ok` с кодом HTTP 410. Для перевыпуска создаётся новая идентичность.
В карточке отдельно видны регистрация отзыва и время последней связи. Протокол
опроса не содержит подтверждения, что носитель завершил блокировку.

Свежий ответ `ok` разрешает оболочке перейти к входу. Полученный ранее отзыв
сохраняется до перевыпуска носителя. Рабочее соединение требует отдельного
допуска на выбранное назначение. [Протокол доступа](ACCESS-PROTOCOL.md)

## Порядок развёртывания

Сервер ставится **первым и в одиночку**: приложения на этот момент ещё нет, и
взять из него нечего. Отсюда весь порядок.

```
sh packaging/revocation-server/install.sh --domain revoke.example.org
```

Сценарий ставит зависимости, создаёт ключ отзыва, поднимает службу и nginx с
сертификатом, а в конце печатает две строки — адрес и **одноразовый код
знакомства**:

```
Адрес для приложения:  https://revoke.example.org
Код знакомства:        2ca0f7915ca816e0cc2161263461b8ed
```

Их администратор вводит в приложении при первой настройке. Дальше приложение
делает всё само: забирает открытую часть ключа отзыва (`GET /pubkey`) и
отправляет свою (`POST /admin/enroll` с кодом в заголовке). Код после этого
сгорает.

**Почему код, а не просто «первый, кто постучится».** Ресурс общедоступен;
без кода его мог бы занять кто угодно, узнав адрес. Альтернатива — заходить на
сервер по SSH и класть ключ руками — означала бы, что у администратора носителей
есть права на сервере, а их у него быть не должно.

Код сгорает под блокировкой и **до** записи ключа администратора: два
одновременных знакомства с одним кодом проходят ровно одно. Кривое тело
(не открытый ключ) код не сжигает — оно разбирается раньше.

Второй администратор заводится новым кодом, его выписывает владелец сервера:

```
openssl rand -hex 16 | tee /var/lib/poa-revocation/enrollment-code
```

Повторный запуск установки безопасен: существующий ключ отзыва не трогается —
перевыпуск сделал бы бесполезными все выпущенные носители, они проверяют подпись
прежним открытым ключом.

## Носитель спрашивает

```
GET /v3/media-state
X-POA-Media: <идентификатор: «приставка-носитель», 8+8 hex; до 1.1.0 — 8 hex>
X-POA-Nonce: <32 hex>
X-POA-Info: version=<версия>;machine=<8 hex отпечатка машины>
X-POA-Signature: <base64 подписи ключом носителя>
```

Подписана строка `poa-ask-v3 <id> <nonce> <info>` без перевода строки, ключом
носителя (Ed25519). Его открытую часть сервер получил при выпуске носителя.
Версия — `[0-9A-Za-z.+~-]`, до 32 знаков.

**Почему в заголовках, а не в адресе.** Адрес оседает в журналах посредников,
заголовки — нет, и по адресу в браузере запрос не повторить.

Ответ `200`, `text/plain`, `Cache-Control: no-store`:

```
poa-state-v3 <media_id> <nonce> <ok|revoked>
<подпись первой строки в base64>
```

Первая строка подписывается **целиком, как есть, без завершающего перевода
строки**, ключом отзыва. Подпись — Ed25519, сырая, в base64.

**Всё прочее — `403` с одним и тем же телом:** нет или кривые заголовки,
неизвестный носитель, у записи нет ключа, подпись не сходится, случайное число
уже встречалось. Одинаковый ответ не подсказывает перебирающему, на каком шаге
он споткнулся.

Сервер принимает запрос от носителя с зарегистрированным при выдаче ключом.
Перед подписью ответа сервер в одной транзакции сверяет актуальный ключ,
сохраняет число запроса и считывает действующее состояние носителя.

**Почему случайное число, а не время.** Это защита от повтора старого ответа.
Носитель переносной, часам его доверять нельзя: батарейка садится, время
сбрасывается. Подписав число, которое носитель прислал сию секунду, сервер
делает вчерашний ответ бесполезным без всяких часов.

**Повтор запроса.** Случайные числа сервер помнит 7 дней (таблица `nonces`,
старые чистятся при каждом успешном запросе); повтор — 403. Без этого
перехваченный запрос отмечал бы в учёте живым носитель, который давно не
включался. Число запоминается только после проверки подписи — посторонний
таблицу не забьёт. Граница: запрос старше 7 дней, перехваченный целиком,
пройдёт повторно — в самом запросе нет времени, которому можно доверять.

**Почему подпись, а не только HTTPS.** HTTPS проверяется цепочкой
удостоверяющих центров, лежащей в самой системе носителя, — то есть тем, что
злоумышленник с носителем в руках может подменить. Подпись проверяется ключом,
который положил администратор. HTTPS при этом обязателен по другой причине: по
открытому каналу видно, какие носители у организации есть и когда включаются.

`GET /state` протокола 1.0.0 отвечает `403`: носителей 1.0.0 в работе нет.

### Учёт последней связи

При успешном запросе сервер запоминает в записи носителя время (UTC, ISO),
версию и отпечаток машины из `X-POA-Info`. Это учёт парка: администратор видит
его на экране отзыва носителя. Повтор числа учёт не сдвигает.

## Администратор выпускает и распоряжается

```
POST /admin/media/<идентификатор>
X-POA-Key-Id: <отпечаток ключа полномочий, 16 знаков>
X-POA-Signature: <подпись тела в base64>

poa-media <идентификатор> <номер> <ok|revoked> [<ключ носителя: base64 сырых 32 байт>]
```

Ответы: `201` — запись заведена, `204` — запись изменена, `403` — ключ не
допущен, подпись не сходится или носитель принадлежит другому администратору,
`409` — номер не больше уже известного серверу, `400` — команда не разобрана,
в том числе нет ключа носителя у новой записи.

**Ключ носителя обязателен при заведении записи.** Без него носитель не сможет
подписать запрос и получал бы только 403. Приложение шлёт ключ при каждой
команде; тот же ключ ничего не меняет, другой — **перевыпуск** носителя с тем
же идентификатором. Команда из четырёх полей принимается только для уже
заведённой записи, ключ остаётся прежним. У носителей, записанных до 1.1.0,
ключа нет: приложение говорит «перезапишите носитель» вместо безликого 400.

**Команда всегда про один носитель, а не про весь список.** Администраторов в
организации несколько. Публикация списка целиком означала бы, что любой из них
переписывает чужие записи — в том числе снимает отзыв, поставленный другим.

**Владелец записи — тот, кто носитель выпустил.** Идентификатора нет в базе —
значит носитель выпускается сейчас: запись заводится, владельцем становится
предъявивший ключ. Идентификатор есть — команду принимают только от того же
ключа. «Прочитать запись — сверить — записать» идёт под блокировкой: два
одновременных выпуска одного идентификатора разными администраторами не
перепишут друг друга.

**Номер строго возрастает,** и у каждой записи он свой. Без него однажды
подписанную команду «этот носитель в порядке» можно было бы прислать повторно и
оживить отозванный.

**Администратор не имеет на сервере никаких прав, кроме этого.** Ни доступа к
оболочке, ни возможности прочитать ключ подписи, ни управления службой. Он лишь
подписывает команду ключом, который не покидает его контейнера.

Нечисловой или отрицательный `Content-Length` в любой команде — `400`.

## Администратор спрашивает о носителе

```
GET /admin/media/<идентификатор>
X-POA-Key-Id: <отпечаток>
X-POA-Time: <unix-время>
X-POA-Signature: <подпись строки "poa-query <id> <время>">
```

Ответ `200`: `poa-record <id> <ok|revoked> <последняя связь ISO|-> <версия|-> <машина|->`.
`403` — ключ не допущен, подпись не сходится, время вне окна ±300 с или
носитель чужой. `404` — такого носителя сервер не знает (только допущенному
администратору с верной подписью).

**Окно времени, а не случайное число.** Часам машины администратора доверять
можно, в отличие от переносного носителя; запрос только читает, и повтор в
пределах пяти минут отдаёт тот же ответ и ничего больше.

## Три ключа и границы между ними

| Ключ | Где закрытая часть | Что даёт его утечка |
|---|---|---|
| Отзыв (подпись ответов носителям) | **только на сервере** — он рождается там при установке | отзыв носителей и выдача «ok»: отказ в обслуживании либо сеанс на отозванном носителе, лечится выдачей новых |
| Полномочия администратора | только в контейнере | возможность распоряжаться носителями этого администратора |
| Носитель | только на носителе, `/etc/poa/device.key`, 0400 root, на зашифрованном корне | возможность выдавать себя за этот носитель перед сервером |

(Ещё один, обмен конфигурациями между администраторами, к серверу отношения не
имеет и контейнера тоже не покидает.)

Ключ отзыва живёт на сервере в одном экземпляре, и это осознанная граница:
сервер общедоступен и однажды будет взломан. Взлом стоит организации отзыва
носителей, но не подделки обмена конфигурациями и не вычисления кодов
восстановления — те ключи выводятся из семян контейнера. Ключей носителей
сервер не знает: в базе только открытые части.

Обратная сторона: **сервер невосстановим без резервной копии ключа.** Потеряв
`/etc/poa-revocation/revocation-key.pem`, владелец теряет возможность отзывать
уже выпущенные носители — новый сервер подпишет ответ ключом, которого они не
знают. Файл маленький; его место — там же, где остальные ключи организации.

## Что оказывается на сервере

1. `poa-revocation-server.py` в `/usr/local/sbin`, `poa-revocation.service` в
   `/etc/systemd/system`.
2. Ключ отзыва — `/etc/poa-revocation/revocation-key.pem`, права `600`, root.
   Служба получает его через учётные данные systemd: с `DynamicUser=yes` она не
   может прочитать файл сама, а ослаблять права на закрытый ключ нельзя.
3. Открытые ключи допущенных администраторов — `*.pem` в
   `/var/lib/poa-revocation/admins/`. Пишет туда сама служба при знакомстве,
   поэтому каталог в состоянии службы, а не в `/etc`.
4. База — `/var/lib/poa-revocation/media.sqlite`, создаётся сама. Таблица
   `media` (запись носителя: владелец, состояние, номер, ключ носителя,
   последняя связь) и `nonces` (случайные числа за 7 дней).
5. Наружу смотрит nginx с TLS, служба слушает только `127.0.0.1`. Носителям
   открыт `/v3/media-state`, приложению — `/pubkey`, `/admin/enroll`, `/admin/media/`.
6. Репозиторий пакетов при желании живёт на этой же машине: `--repo-root
   <каталог>` раздаёт его как `/repo`.

Администратор, потерявший свой контейнер, теряет и управление своими
носителями: изменить их записи сможет только владелец сервера, руками в базе.
Это цена того, что сервер не может выдать себя за администратора.

## Переход с 1.0.0

Службу и сценарий установки достаточно обновить повторным запуском
`install.sh`: ключ отзыва и база остаются на месте. База 1.0.0 дополняется при
старте службы — недостающие столбцы добавляются `ALTER TABLE`, записи,
владельцы и номера сохраняются, появляется таблица `nonces`.

У перенесённых записей нет ключа носителя, и носитель по ним получает 403.
Ключ появляется у записи со следующей командой владельца из приложения 1.1.0 —
если носитель записан 1.1.0; носитель 1.0.0 нужно перезаписать.

## Что происходит, когда сервер молчит

При недоступности сервера или ошибке проверки носитель пишет событие в журнал
и показывает уведомление. До первого подписанного `ok` запуск приложений
закрыт. Для выбранного рабочего места действует свой срок допуска до 300
секунд от отправки запроса. Потеря связи не продлевает этот срок.
