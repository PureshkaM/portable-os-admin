# Архитектура

Этот документ связывает курсовой проект («Проектирование защищённого
приложения для создания и администрирования переносной операционной системы
на внешнем носителе», КГУ, 2026) с фактической реализацией в этом
репозитории: какой модуль реализует какой класс/вариант использования из
документа, какие решения приняты при переходе от UML-моделей к рабочему
коду, и что осталось непроверенным или сознательно отложенным.

## Технологический стек

- **Python 3.9+**, без C-расширений, кроме `cryptography` (обёртка над
  OpenSSL/BoringSSL для AES-GCM и scrypt).
- **Textual** — TUI-библиотека для интерфейса администратора: три «окна» из
  курсового проекта (открытие/создание контейнера → главный экран → формы
  установки/логов/обмена/восстановления) реализованы как экраны (`Screen`) в
  одном Textual-приложении, а не как отдельные процессы — стек экранов
  (`push_screen`/`pop_screen`) даёт то же ощущение многооконности, что и
  Window flow в исходном WPF-варианте (см. соседний проект
  `WsusThirdPartyPublisher` в этом же рабочем каталоге, где такой подход уже
  применялся).
- **parted / cryptsetup / debootstrap / dnf / mkfs.\*** — внешние системные
  утилиты, вызываемые через `subprocess`, а не переизобретённые на Python.

## Почему всё деструктивное — dry-run по умолчанию

Разработка велась в песочнице без доступа к запасным USB-накопителям и без
привилегий root на реальном Linux-хосте. Поэтому **любая** операция, которая
меняет содержимое диска (`parted`, `cryptsetup`, `mkfs.*`, `debootstrap`,
`dnf --installroot`, `mount`/`umount`), проходит через единственную точку —
`install/command_runner.py:CommandRunner.run()` — которая:

1. По умолчанию (`dry_run=True`) **не выполняет** команду, а только
   записывает её в `CommandPlan` для последующего анализа/логирования/теста.
2. Для реального выполнения (`dry_run=False`) требует **повторного**
   указания пути устройства в `confirm_device` — простая защита от случайного
   запуска установки не на том диске из-за опечатки в UI.

Это касается `DiskManager`, `LuksManager`, `OSInstaller`,
`LogViewer`/`ExchangeManager`.

**Обновление:** у пользователя появилась реальная Linux-машина (RedOS, с
полным доступом к зеркалам RedOS/Astra/BaseAlt) для тестирования настоящей
установки, поэтому `tui/screens/install.py` теперь предоставляет способ
включить `dry_run=False` — но не безусловно: экран добавляет отдельный
переключатель («Реальное выполнение») плюс обязательное повторное указание
пути устройства (`confirm_device`), и только когда оба совпадают, вызывается
`installer.run(..., dry_run=False, confirm_device=...)`. Это UI-level
подтверждение не заменяет проверку в `CommandRunner.run` — оно ровно то же
самое требование, просто явно показанное пользователю перед тем, как он
вообще нажмёт кнопку с реальным выполнением. Несмотря на то что путь теперь
доступен, статус "проверено на реальном железе" присваивается только по
факту подтверждённого пользователем успешного запуска — тот же принцип
честности, что и в `WsusThirdPartyPublisher`: «Treat any claim about runtime
behavior as unverified until the user confirms a real run».

## Модель разметки диска

`install/disk.py` реализует ровно ту структуру разделов, что описана в
§1.4.3 и на диаграмме развёртывания: `POA_BOOT` (FAT32/ESP) →
`POA_SYSTEM` (LUKS2, всё оставшееся место за вычетом двух следующих
разделов) → `POA_LOGS` (ext4) → `POA_EXCHANGE` (ext4). Разделы логов и
обмена — **обычные незашифрованные ext4-разделы вне LUKS-контейнера**, а не
часть системного раздела: это явно следует из диаграммы развёртывания
документа (§4.4, четыре отдельных раздела на носителе) и подтверждается
таблицей мер защиты §3, где для раздела обмена указано «доступ через
установленную систему», а не «шифрование». Это ключевое архитектурное
решение: оно позволяет `LogViewer`/`ExchangeManager` работать **без**
LUKS-пароля пользователя — администратор монтирует `POA_LOGS`/`POA_EXCHANGE`
напрямую.

## Идентификация носителя без раскрытия LUKS

Раздел `POA_BOOT` содержит файл `poa/media_id.txt`, записанный при установке
(`OSInstaller._install_boot_environment`). `admin/media_lookup.py` читает
этот файл и сопоставляет `media_id` с `MediaRecord` в контейнере —
это реализация «Журналы.Носитель.Сопоставление» / «Обмен.Носитель.Сопоставление»
без необходимости открывать зашифрованный системный раздел.

## Схема кода восстановления

Требование «Восстановление.Код.НеПароль» реализовано буквально:

1. При установке генерируется случайный человекочитаемый `recovery_code`
   (`crypto.generate_recovery_code()`, формат `XXXX-XXXX-XXXX-XXXX`).
2. Реальная LUKS-парольная фраза recovery-keyslot'а —
   `scrypt(recovery_code, recovery_salt)` (`crypto.derive_recovery_passphrase`),
   **не** сам код.
3. В контейнере администратора хранится `recovery_code` (внутри
   зашифрованного контейнера) и `recovery_salt` — этого достаточно, чтобы
   выдать код администратору повторно предъявить пользователю, но сам код
   никогда не передаётся по сети и не виден вне контейнера/диалога
   администратор-пользователь.
4. Запрос восстановления — текстовая строка `media_id:slot:checksum`
   (`recovery/request.py:RecoveryRequest`), где `checksum` защищает от
   опечаток при устной/письменной передаче (УИ-7, «Запрос восстановления
   некорректен»).
5. Recovery-запись имеет только два состояния: `available` → `used`.
   Повторная выдача кода для одной и той же записи невозможна
   (`Восстановление.RecoveryЗапись.Недоступна`).

## Бэкенды установки ОС

Три поддерживаемых цели (`config.target_os`), реализующие общий
`install/backends/base.py:InstallBackend`:

| Цель | Bootstrap | Особенности, подтверждённые вживую |
| --- | --- | --- |
| `debian` (Debian/Ubuntu) | `debootstrap` | группа sudo — `sudo`, служба SSH — `ssh` |
| `redos` (RedOS) | `dnf --installroot` | группа sudo — `wheel`, служба SSH — `sshd`; репозитории/релизы/группа `@core` проверены напрямую по `repo1.red-soft.ru` (см. "Известные ограничения" ниже) |
| `astra` (Astra Linux) | `debootstrap` (наследует `DebianInstallBackend`) | группа sudo — `astra-admin` (**не** `sudo`); требует патченный Astra-специфичный пакет `debootstrap` на хосте-администраторе (suite-имена `orel`/`voronezh`/`smolensk` не распознаются апстримным debootstrap) |

BaseAlt/Alt Linux **не** реализован как цель установки — см. следующий
раздел.

## Просмотр пакетов из реального репозитория (`config/repo_browser.py`)

Чтобы не заставлять администратора набирать точные имена пакетов по памяти
при заполнении `config.packages`, `PackageBrowserScreen` (доступен из экрана
конфигураций кнопкой «Пакеты...») подключается напрямую к репозиторию цели
и показывает реальный список пакетов с версией/описанием:

- **`AptPackageSource`** (Debian, Astra) — читает apt-индекс
  `<mirror>/dists/<release>/main/binary-amd64/Packages.gz`. Проверено
  напрямую против `deb.debian.org/debian/dists/bookworm`.
- **`DnfPackageSource`** (RedOS) — читает `repodata/repomd.xml`, затем
  primary-метаданные. Проверено напрямую против
  `repo1.red-soft.ru/redos/8.0/x86_64/os`: метаданные там сжаты **zstd**
  (`*-primary.xml.zst`), не gzip, поэтому модуль вызывает системную утилиту
  `zstd` (тот же класс внешней зависимости, что `parted`/`cryptsetup` в
  остальном проекте) вместо добавления pip-зависимости `zstandard` ради
  одного этого запроса.

Оба источника — только HTTP GET по публичным метаданным, ничего
деструктивного не выполняется, поэтому этот модуль не проходит через
`CommandRunner`'овский dry-run gate.

## Упаковка (`packaging/`)

`.deb` (Debian/Ubuntu/Astra) и `.rpm` (RedOS/RHEL-семейство) для установки
самого приложения на администраторскую машину — подробности, включая
обоснование венва вместо системных Python-пакетов (системный
`python3-textual` в Debian bookworm — версии 0.1.13, до полного
переписывания библиотеки, несовместим с `textual>=0.58`, на котором
построен этот проект), в `packaging/README.md`. Ни один из пакетов не
собирался и не проверялся из песочницы разработки (нет `dpkg-buildpackage`/
`rpmbuild` на macOS) — сборка тоже часть цикла "собрать на реальной
машине → сообщить об ошибках".

## Известные ограничения (сознательно отложено)

Аналогично рабочему соглашению в `WsusThirdPartyPublisher`, ниже — то, что
**не** стоит достраивать без явного запроса, и то, что помечено как
неподтверждённое до реального теста:

- **Интеграция recovery-скрипта с загрузчиком/initramfs не реализована.**
  `recovery/recovery_module.sh` — рабочий эталонный скрипт (реализует всю
  логику варианта использования УИ-9), но он не подключён к реальному
  GRUB/dracut/initramfs-tools хуку — это отдельная, сильно
  дистрибутив-специфичная инженерная задача. Скрипт также зависит от
  небандлящегося вспомогательного бинаря `poa-recovery-kdf` (scrypt на
  чистом POSIX sh нереализуем) — контракт его CLI описан прямо в скрипте.
- **`dry_run=False` теперь доступен из TUI (см. выше), но ещё не
  подтверждён успешным запуском против настоящего блочного устройства.**
  Планирование команд (`parted`/`cryptsetup`/`mkfs`/`debootstrap`/`dnf`)
  покрыто тестами, реальное выполнение технически разблокировано, но
  фактическое поведение этих утилит на реальном USB-носителе ещё предстоит
  подтвердить на реальной машине пользователя (RedOS).
- **RedOS: репозитории/релизы/группа `@core` проверены, GPG-ключ — нет.**
  Прямой проверкой `repo1.red-soft.ru` подтверждено: актуальные ветки —
  `7.3` и `8.0` (releasever — ровно эта строка), группа `@core` реально
  существует в comps.xml обеих веток, `openssh-server` обязателен в базовой
  группе. **Не подтверждено:** точное имя/путь GPG-ключа
  (`RPM-GPG-KEY-RED-SOFT` — не более чем правдоподобное предположение) —
  перед реальным запуском стоит свериться с `/etc/yum.repos.d/*.repo`
  `gpgkey=` прямо на тестовой машине, а не доверять этому файлу документации.
- **BaseAlt/Alt Linux сознательно не реализован как цель установки** (после
  явного решения пользователя отложить, а не строить на непроверенном
  механизме). Исследование не нашло документированного способа
  bootstrap'а корневой файловой системы Alt Linux с чужого хоста: штатный
  инструмент — `hasher` (`hasher-priv`), но он сам требует уже установленной
  apt-rpm/Alt-системы с привилегированным suid-хелпером — работающего
  аналога `debootstrap`/`dnf --installroot` для этого случая не
  задокументировано. Вернуться к этому стоит только когда появится реальный
  Alt Linux хост для проверки `hasher` напрямую, а не раньше.
- **Astra Linux: debootstrap-путь подтверждён, но с оговоркой.** Astra CE
  ("orel") — ребрендинг Debian 9; однако Astra распространяет собственный
  патченный пакет `debootstrap` (суффикс вида `astra7`) со скриптами для
  suite-имён `orel`/`voronezh`/`smolensk` — апстримный debootstrap эти имена
  может не распознать. Хосту-администратору нужен именно Astra-шный
  `debootstrap`, что этот проект установить не может (это должно быть уже
  на хосте). Также не подтверждено имя keyring-пакета для доверия
  Astra-репозиториям.
- **Диаграмма потоков данных / деревья опасностей / DREAD** из курсового
  проекта не переносились в код напрямую — они формировали требования
  (см. таблицу трассировки выше), а не отдельный программный артефакт.
- **Постоянный пароль ОС-уровня не назначается.** `useradd` создаёт учётную
  запись, но `passwd -l` сразу блокирует пароль — единственный секрет
  «переднего входа» в переносную систему это LUKS-пароль, заданный при
  установке. Это решение, а не недоработка: в документе нет отдельного
  варианта использования на смену OC-пароля пользователя, только LUKSпароль и код восстановления.
- **Категории апробации (STRIDE/DREAD) как автоматические проверки** —
  не реализованы как runtime-проверки; они были входом для решений
  (например, `Конфигурация.Использование.Запрет`), но нет отдельного
  «threat-model линтера» в коде.

## Локализация и UI

В отличие от `WsusThirdPartyPublisher`, этот проект **не** делает
русский/английский билингвизм первоклассной функцией — интерфейс и
сообщения на русском языке (как в исходном документе), без отдельного слоя
локализации. Если потребуется английский UI — стоит выделить строки в
отдельный модуль по образцу `WsusThirdPartyPublisher/Localization/Strings.cs`,
но это не делалось, так как не запрашивалось.
