# Рутокен ЭЦП: изученный экземпляр (08.10.2026)

Справка, чтобы к токену больше не возвращаться: что за устройство, что оно умеет,
как его подпись стыкуется с нашей криптографией и что из этого следует для LIVE-2.0.
Все факты сняты на стенде `posvm` зондом
[`tools/stand/rutoken-probe.py`](../tools/stand/rutoken-probe.py), кроме помеченных
«по документации производителя». Программу (`src/`) это изучение не меняло.

## Коротко

- **Для основного корня организации (Э18) годится полностью.** Ключ ГОСТ Р 34.10-2012
  256 на нашей кривой `id-tc26-gost-3410-2012-256-paramSetA` рождается в чипе и не
  извлекается. Подпись чипа проверяется нашим `poa_gost.verify` **как есть**, без
  перестановок байтов; «Стрибог-256» чипа бит в бит равен `poa_gost.streebog`.
- **Носителем быть не может:** флеш-памяти нет, только чип (USB CCID). Для токена-носителя
  (`TOKEN_DRAFT`, ступень с `kexec`) по-прежнему нужен Рутокен ЭЦП 2.0 Flash (серия 4500).
- **Ключ носителя на чипе** (на будущее, для токена-носителя того же семейства): работают
  и ГОСТ, и ECDSA P-256 (подпись r‖s проверяется `cryptography`). Ed25519 нет.
- **Нужна библиотека Актива** `librtpkcs11ecp.so`: OpenSC токен видит, но работать с ним
  не может. Её нет ни в одном из наших образов.
- **PIN заводские** — перед тем как класть корень, сменить оба.

## Экземпляр

| Что | Значение |
|---|---|
| USB | `0a89:0030` «Aktiv Rutoken ECP», класс 0x0B (CCID), USB 2.0, 100 мА, серийного номера в дескрипторе нет; только CCID, без накопителя |
| ATR | `3B 8B 01 52 75 74 6F 6B 65 6E 20 44 53 20 C1` («Rutoken DS», T=1) |
| PKCS#11 (`C_GetTokenInfo`) | модель `Rutoken ECP`, серийный `471a4f76`, аппаратная версия **67.4**, прошивка **32.2**, метка `Rutoken ECP <no label>` |
| Расширенно (`C_EX_GetTokenInfoExtended`) | класс ECP, тип 0x1, протокол 4, микрокод 32, заказ 2; память **128 КБ**, свободно 87 008 Б (0 объектов) |
| Флаги | `ADMIN_CHANGE_USER_PIN`, `USER_CHANGE_USER_PIN`, `SUPPORT_JOURNAL`; **нет** `HAS_FLASH_DRIVE`, `SUPPORT_SECURE_MESSAGING`, `ADMIN/USER_PIN_NOT_DEFAULT` |
| PIN | пользователь и администратор: длина 6–249, по 10 попыток. PIN пользователя заводской `12345678` (вход им проверен); администратора — заводской по флагу, по документации производителя `87654321` (входом не проверялся) |

**Модель.** Программно её не узнать: поле `model` у всего семейства одно — «Rutoken ECP»,
объектов `CKH_VENDOR_TOKEN_INFO` (атрибут `CKA_VENDOR_MODEL_NAME`) эта связка библиотеки и
прошивки не отдаёт; производитель на своём форуме подтверждает, что модели через PKCS#11
нет. По признакам — прошивка 32.x, RSA до 4096, ECDSA до P-521, 128 КБ, без флеш-памяти —
это **Рутокен ЭЦП 3.0** (вывод, не факт). Точно — четыре цифры серии на корпусе: 3100,
3120, 3220 — ЭЦП 3.0; 2000–2200, 4000–4500 — ЭЦП 2.0
([маркировка](https://dev.rutoken.ru/pages/viewpage.action?pageId=57147638)).

## Механизмы

Все — аппаратные (`hw`), список `C_GetMechanismList` целиком снимается
`pkcs11-tool --module … -M`.

| Семейство | Что есть |
|---|---|
| ГОСТ Р 34.10-2012 | 256 и 512: генерация, подпись хеша (`CKM_GOSTR3410`), подпись со «Стрибогом» (`CKM_GOSTR3410_WITH_GOSTR3411_12_256/512`), VKO/derive |
| ГОСТ Р 34.11-2012 | «Стрибог» 256 и 512, HMAC; старый 34.11-94 |
| Кривые 256 бит | генерация на чипе проверена: tc26 paramSetA, tc26 paramSetB, CryptoPro-A, CryptoPro-XchA |
| Блочные ГОСТ | 28147-89 (с key wrap и MAC), «Магма» и «Кузнечик» (вендорские `0xD432102D…0xD4321037`) |
| ECDSA | ключ 256–521 бит, хеши SHA-1…SHA-512; ECDH (от 255 бит) |
| RSA | 512–4096: PKCS#1 v1.5, PSS, OAEP |
| EdDSA | **нет** (`CKM_EC_EDWARDS_KEY_PAIR_GEN`, `CKM_EDDSA` отсутствуют) |
| Прочее | ГСЧ (`C_GenerateRandom`), SHA-1/2, MD5 — программно в библиотеке |

## Сверка с нашей криптографией

Прогон `rutoken-probe.py check` 08.10.2026 (ключи временные, после проверки удалены):

| Проверка | Итог |
|---|---|
| Генерация ГОСТ-256 paramSetA на чипе | 0,28 с; атрибуты закрытого ключа: `SENSITIVE`, `NEVER_EXTRACTABLE`, `ALWAYS_SENSITIVE`, `LOCAL` = да, `EXTRACTABLE` = нет; чтение `CKA_VALUE` закрытого — отказ |
| Открытый ключ (`CKA_VALUE`) | 64 байта **x‖y, каждое little-endian** — у нас (`poa_gost.encode_public`) x‖y big-endian: при чтении развернуть каждую половину |
| «Стрибог-256» чипа (`CKM_GOSTR3411_12_256`) | равен `poa_gost.streebog(data, 256)` бит в бит |
| Подпись `CKM_GOSTR3410_WITH_GOSTR3411_12_256` | 64 байта, 0,05 с; `poa_gost.verify` принимает **как есть** — тот же формат s‖r big-endian, что у нас и у OpenSSL gost-engine |
| Подпись готового хеша `CKM_GOSTR3410` | хеш подаётся в том виде, в каком его возвращает `poa_gost.streebog`; развёрнутый — не сходится |
| ECDSA P-256 | генерация 0,18 с, подпись 0,04 с, r‖s по 32 байта big-endian; `cryptography` проверяет после `encode_dss_signature` |

Тонкости шаблонов (иначе `CKR_TEMPLATE_INCONSISTENT`):
- ГОСТ: `CKA_GOSTR3410_PARAMS` (OID кривой) **и** `CKA_GOSTR3411_PARAMS`
  (`1.2.643.7.1.1.2.2`, «Стрибог-256») — в обоих шаблонах пары.
- ECDSA: `CKA_EC_PARAMS` — **только** в шаблоне открытого ключа.

Память: первое создание объекта съело 448 байт однократно (служебный каталог PKCS#11);
повторные создания и удаления ключей память не трогают. На корень и сертификаты места с
запасом.

## Что это значит для проекта

- **Основной корень (Э18) — разблокирован.** Подписант «корень на токене» — тот же
  интерфейс, что у `poa_trust.GostSigner` (`alg`, `entry`, `sign`): `alg` — уже существующий
  `gost2012-256-A`, `entry.key` — `CKA_VALUE` с развёрнутыми половинами, `sign` —
  `CKM_GOSTR3410_WITH_GOSTR3411_12_256` по `canonical(body)`. Формат документов, проверка
  на носителе и резервный корень не меняются. Ключ создаётся на чипе с
  `CKA_TOKEN`, `CKA_PRIVATE`, `CKA_SENSITIVE`, без `CKA_EXTRACTABLE`, ищется по `CKA_ID`;
  метку токена (`C_EX_SetTokenName`) — например, `poa-root-main`.
- **Токен-носитель** ждёт другого устройства (с флеш-памятью). Вопрос «P-256 или ГОСТ для
  ключа носителя» решается не возможностями чипа (есть оба), а стороной сервера: P-256
  проверяет `cryptography` без нашей реализации, ГОСТ — `poa_gost`.
- **Белый список `/smartcard` по VID:PID** не отличит модели: `0a89:0030` у всего семейства
  ЭЦП 2.0/3.0 (Рутокен S — `0a89:0020`, Lite — `0a89:0025`,
  [RU1013](https://dev.rutoken.ru/display/KB/RU1013)). Исключать носитель-токен из проброса
  придётся по серийному номеру или пути USB, не по VID:PID.
- **Журнал операций** (`C_EX_GetJournal`, 126 байт) от обычных подписей не меняется: он
  ведётся только для ключей с `CKA_VENDOR_KEY_JOURNAL` (сценарии ДБО), формат не
  опубликован. Счётчиком использования корня он не служит.

## Окружение

Цепочка: `pcscd` + `libccid` (драйвер CCID; `ifd-rutokens` на стенде — для Рутокен S, этому
не нужен) → `librtpkcs11ecp.so` (PKCS#11 Актива) → наш код через ctypes.

- **OpenSC 0.26 не годится:** драйвер `rutoken_ecp` карту узнаёт, но PKCS#15 на ней нет
  («Unsupported card»), PKCS#11-модуль OpenSC отвечает `token not recognized`.
  Переразмечать токен под PKCS#15 — значит отказаться от разметки производителя.
- **Библиотека Актива:** 2.21.1.0 от 19.08.2026,
  `https://download.rutoken.ru/Rutoken/PKCS11Lib/Current/` — Linux x64 (`.deb`, `.rpm`,
  `.so`) в `Linux/x64/`, aarch64 и прочие — в `Linux/others.zip`; заголовки (`rtpkcs11*.h`,
  `pkcs11tc26_*.h`) — в `include/`. Закрытая, бесплатная; условия распространения в
  составе нашего продукта **не проверялись** — до включения в поставку прочитать лицензию.
- **В образах:** РЕД ОС 8 (ISO) — `pcsc-lite`, `pcsc-lite-ccid`, `opensc`,
  `openssl-gost-engine`; библиотеки Актива нет. Debian 13 DVD-1 — только `libpcsclite1`;
  `pcscd` и `libccid` — из `deb.debian.org`.
- Корень нужен на машине администратора, не на носителе: в образ носителя PKCS#11 и
  утилиты по-прежнему не кладём (решение «Токены на рабочем месте»).

## Риски

- **PIN идёт по USB открытым текстом:** защищённого канала (secure messaging) у экземпляра
  нет. Троян на машине администратора перехватит PIN — но не ключ: подписывать без самого
  токена нельзя. Мера — подключать корень только к доверенной машине администратора на
  время подписи.
- **Заводские PIN** у обоих ролей; флаги позволяют сменить PIN пользователя и
  администратору, и самому пользователю. 10 неверных PIN пользователя — блокировка до
  разблокировки PIN администратора; заблокированный PIN администратора, насколько
  известно о Рутокене, снимается только форматированием (не проверялось), а оно
  уничтожает корень. Отсюда и резервный корень-файл.
- **Закрытая библиотека** выполняется в процессе программы администратора; обновлять
  только с сайта производителя и сверять sha256.
- **Подпись ГОСТ не постквантовая** — граница токена, уже учтена в решении о корне.

## Стенд

На `posvm` (Debian 13 aarch64 под UTM, токен проброшен в ВМ):

| Путь | Что |
|---|---|
| `/root/rutoken/lib/librtpkcs11ecp.so` | библиотека aarch64, sha256 `c9e51c12b080549dde4d06bdc14d380a8a8eb416b80c2a6fd1ad108cdb298ca3`; рядом её `.deb` (`f984bbd082682ed4183f86d69deff60ed805ef04e7f3b5197ba0cbbe1ead3719`), в систему не установлена |
| `/root/rutoken/include/` | заголовки Актива |
| `/root/rutoken/dl/others.zip` | исходный архив (105 МБ; можно удалить) |
| `/root/rutoken/rutoken-probe.py` | копия зонда из `tools/stand/` |

```
ssh posvm 'python3 /root/rutoken/rutoken-probe.py info'           # без PIN, ничего не меняет
ssh posvm 'cd /root/rutoken && python3 rutoken-probe.py check'     # PIN: POA_TOKEN_PIN или заводской
```

`check` после смены PIN без `POA_TOKEN_PIN` откажется сам: неверный PIN тратит попытку.
