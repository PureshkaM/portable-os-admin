## Контекст

Сейчас `portable-os-admin`:
- собирает РЕД ОС 8 или Debian 13 (MATE/KDE) в squashfs и разворачивает на флешку: GPT, LUKS, overlay с постоянным верхним слоем;
- обновляет носитель пакетами;
- VPN и RDP не держит в базе;
- конфигурацию доступа пользователю не доставляет.

Задачи Максима:
1. LiveCD с прежними требованиями к безопасности.
2. Обновление системы целиком без участия администратора.
3. OpenVPN и клиенты RDP/VNC/SSH вместо проприетарных решений, с возможностью вернуть ViPNet.
4. Защищённая доставка доступа. Угроза: у злоумышленника копия флешки и ссылка TOTP. При этом пользователь вводит только фразу LUKS (на токене — PIN), TOTP и пароль рабочей машины.

Решения согласованы с Максимом 30.09–01.10.2026. Каждое прошло проверку на необходимость (раздел «Обоснование»): что не нашло весомой причины, переработано или упразднено.

Пересматриваются явно, записать в README:
- «система ставится с локального образа по умолчанию» (`README.md:3697`) — **решение Максима 01.10.2026:** LiveCD собирается из максимально обновлённых пакетов: официальный репозиторий, записанный в самом образе (Debian — `deb.debian.org` с обновлениями и безопасностью, РЕД ОС — её репозиторий), либо локальный репозиторий компании вместо него. Образ остаётся источником сведений о семействе и выпуске (Э22);
- «VPN/RDP в базе нет» (`README.md:2480`);
- «верхний слой постоянный» (`overlay.py:41-45`);
- «dm-verity отложен» (`PLAN.md:185`).

«Эталон в squashfs» остаётся.

## Принципы

1. **В образе нет секретов.** Секреты живут в хранилище носителя или выдаются сервером.
2. **Доверяем подписи, а не месту хранения.** Неизменяем только корневой открытый ключ.
3. **Один путь загрузки для флешки и токена.** Различие одно: защищён ли от записи раздел загрузки.
4. **Наш сервер только разрешает и запрещает.** Трафик пользователей идёт через VPN-шлюз компании в DMZ. Шлюз доверяет нашему CA и не опрашивает сервер на каждое подключение (модель ViPNet).
5. **На носителе по умолчанию закрыт весь трафик.**
6. **Стандартная криптография вместо своей,** где стандартная закрывает ту же угрозу.

## Топология

```
носитель → интернет → внешний МЭ → DMZ: [VPN-шлюз компании] [сервер доступа: 1 узел или кластер ≥3]
                                     → внутренний МЭ → рабочие машины (RDP / VNC / SSH)
```

Шлюз использует только штатные настройки OpenVPN: `ca` — наш CA, `crl-verify` (таймер раз в минуту забирает CRL; CRL в каталоге, читаемом от `nobody`), `reneg-sec 900`, `tran-window 60`, `persist-key`, UDP плюс запасной TCP 443. Сегментацию по целям делает внутренний МЭ компании, на стенде — `ccd` плюс nftables.

## Сценарий пользователя

1. Загрузка. Флешка — фраза LUKS, токен — PIN токена.
2. Окно «Подключение» со списком сетей. Если сеть уже есть, этот шаг пропускается.
3. HTTP-проба нашего сервера. Если ответ подменён, это портал: открывается запертое окно портала.
4. `/v2/state`, он же проверка отзыва. После «ok» появляется поле TOTP, при первом запуске — активация.
5. TOTP и звено уходят на сервер, в ответ приходит доступ к VPN на 24 часа. Ключ VPN только в RAM.
6. Подключение VPN.
7. Проверка целей по TCP. Если целей несколько — список. Недоступная цель даёт одно из двух сообщений: «не отвечает» или «отклонила подключение».
8. Окно пароля рабочей машины.
9. Сеанс на весь экран:
   - RDP: `xfreerdp /f /sec:nla /from-stdin`, закреплённый сертификат, без проброса дисков и USB, буфер обмена только текстовый, `/smartcard` по флагу цели;
   - VNC: своё окно на GtkVnc, только VeNCrypt X509Plain (VNC-клиента нет ни в одном образе — Э0);
   - SSH: своё окно на VTE, запускающее только `ssh` с `EscapeChar=none`, без агента, X11 и пробросов, ключ хоста закреплён (`xterm` нет в РЕД ОС — Э0).

После выхода из сеанса — «Подключиться снова», без повторного TOTP, пока жив доступ к VPN.

## Устройство носителя

**Флешка:**

| # | Область | Содержимое | Защита |
|---|---|---|---|
| 1 | Загрузка (ESP) | shim, grub, проверяющая ступень, корневой ключ, `medium.cfg` | RW, только обнаружение подмены |
| 2 | Ядра слотов | ядро и initrd A/B, `slot-state` | RW, подпись |
| 3 | Образы | squashfs A/B и verity | RW, без шифрования, подпись и verity |
| 4 | Хранилище | `device.key`, звено, описатель сервера, ViPNet, Wi-Fi, настройки провайдера, `min_serial`, ключ журналов | LUKS: фраза, машинные слоты, коды восстановления |
| 5 | Журналы | очередь событий ИБ, ограниченная диагностика | LUKS, пишет только root |

**Токен** (Рутокен ЭЦП 2.0 Flash):

| # | Где | Содержимое | Защита |
|---|---|---|---|
| — | чип | ключ носителя (не извлекается), ключ для разворачивания ключа хранилища, PIN пользователя с блокировкой, PIN администратора | аппаратная |
| 1 | RO или CD-ROM | ESP, проверяющая ступень, корневой ключ | без PIN администратора не изменить |
| 2 | RW | ядра слотов | подпись |
| 3 | RW | образы | подпись и verity |
| 4 | RW | хранилище (без звена и `device.key`: их заменяет чип) | LUKS, ключ из чипа после PIN |
| 5 | RW | журналы | LUKS, пишет только root |

Скачанное не касается рабочих областей до проверки, у обоих носителей одинаково:
- образ пишется в неактивный слот, а тот не загружается, пока не проверен;
- конфигурация пишется во временный файл, после проверки подписи атомарно переименовывается.

## Загрузка и обновление

- **Проверяющая ступень** — ядро плюс наш initramfs на ESP:
  1. читает `slot-state`;
  2. проверяет подпись выпуска рабочим ключом, сертификат которого подписан корнем;
  3. сверяет sha256 ядра и initrd;
  4. уменьшает счётчик попыток;
  5. передаёт управление ядру слота через `kexec_file_load`.

  После трёх неудач загружается прежний слот.
- **Initramfs слота:**
  1. разблокирует хранилище;
  2. проверяет `serial ≥ min_serial` (антиоткат);
  3. `veritysetup` для squashfs;
  4. верхний слой в tmpfs, затем overlay;
  5. монтирует нужное из хранилища через bind.
- **Общий initramfs.** Всё, что сейчас вшито в каждый носитель (mapper `debian.py:304`, `redos.py:335`; UUID `installer.py:61-99`; `media_id` `machine_binding.py:294`; crypttab `tables.py:58`; `grub.cfg` `base.py:714`; `revocation/script.py:33`), уходит в `medium.cfg` и хранилище. Сборка initramfs переезжает из `installer.py:837` в `_build_root` (`:495`).
- **Обновление:**
  - сервер в ответе на вход сообщает назначенный выпуск;
  - `poa-image-update` скачивает его с сервера доступа в неактивный слот через `Range` и `ionice`, проверяет подпись, sha256 и verity;
  - уведомление «Не выключайте компьютер…» плюс `systemd-inhibit` на время записи;
  - по окончании — «применится при следующем включении»;
  - ниже `min_serial` сервер отвечает `426`, и обновление идёт из окна;
  - вручную: администратор пишет слот программой, LUKS открывать не нужно — образы не зашифрованы.

## Сервер доступа

### Канал «носитель ↔ сервер»
- **TLS 1.3.** Самоподписанный сертификат сервера закреплён по отпечатку ключа в описателе сервера. PFS даёт сам TLS (ECDHE), публичные УЦ не участвуют.
- **Аутентификация носителя.** Сервер выдаёт одноразовый nonce, носитель подписывает `nonce ‖ эндпоинт ‖ sha256(тело)` ключом носителя: `device.key` или чипом токена через PKCS#11. Повтор невозможен: nonce одноразовый, хранится в базе.
- **Ответы** содержат `server_time`. Описатели и выпуски дополнительно подписаны администратором, потому что их хранят и проверяют позже.

### Эндпоинты
| Запрос | Что делает |
|---|---|
| `POST /v3/nonce` | одноразовый nonce |
| `POST /v3/activate {code}` | семя TOTP и L0; засчитывается после первого входа |
| `POST /v3/session {totp, N, status}` | предложенное N+1 и назначенный выпуск. `status` — подтверждённый слот и версия |
| `POST /v3/session/confirm {N+1, vpn_pub}` | фиксирует N+1, гасит N, выдаёт данные провайдера VPN (OpenVPN: сертификат на 24 часа, CA, `tls-crypt-v2`, шлюзы; ViPNet: пароль `.dst`) и цели |
| `POST /v3/events {batch}` | очередь событий, ответ — подтверждённый `seq` |
| `GET /v3/crl`, `GET /v3/release/…`, `GET /v3/descriptor` | для шлюза и носителей |

**Звено.** C — подтверждённое, P — предложенное, история — хеши всех выданных звеньев.

| Предъявлено | Реакция |
|---|---|
| v = C, P нет | выдать P |
| v = C, P есть | старое P в историю, выдать новое P, записать аномалию |
| v = P | засчитать как подтверждение |
| v в истории | клон: блок носителя, его сертификаты в CRL, событие |
| v неизвестно | отказ |

Звено, `last_step` TOTP и nonce меняются в **одной транзакции с блокировкой строки носителя**.

У токена звена нет. Его роль играет неизвлекаемый ключ в чипе. TOTP для токена — по настройке администратора, по умолчанию выключен: PIN и чип уже дают два фактора.

**Коды ответов:**
- `403` — одинаковое тело на любую неудачу;
- `409 already_activated` / `409 clone`;
- `410` — код активации истёк;
- `423` — носитель заблокирован;
- `426` — нужно обновление;
- `401` — неверный TOTP.

### Управление (как программы в групповых политиках)
- **Группы.** Иерархия групп; носитель входит ровно в одну. Действует ближайшее назначение дистрибутива вверх по дереву. Корень — назначение по умолчанию.
- **Решает сервер.** Носитель проверяет подпись, сквозной `serial` и совместимость: семейство, архитектуру и версию разметки. Несовместимое (другое семейство) сервер не отдаёт, а администратор видит список носителей «перезаписать вручную».
- **Замена дистрибутива.** Администратор сам назначает группам новый дистрибутив. Пометка «заменяет X» — подсказка мастера. Тестирование на устройстве остаётся за администратором.

### Развёртывание
- **PostgreSQL** в обоих режимах (`python3-psycopg2`), данные v2 переносятся из sqlite.
- **Один узел** — приложение и PostgreSQL на одной машине.
- **Кластер ≥3** — на каждом узле приложение, PostgreSQL и etcd, Patroni, синхронная репликация. Нагрузку распределяет сам носитель, выбирая адрес случайно. Кворум исключает раздвоение базы.
- `install.sh` знает роли `single`, `cluster-node`, `add-app-node`. Секреты раскладываются через `LoadCredential`.

### Описатель сервера и ключи администратора
- **Описатель** — около 1 КБ, подписан рабочим ключом. Поля: `serial`, адреса узлов, отпечаток TLS, отозванные ключи сервера, резервные места поиска.
  - Хранится в хранилище носителя; каждый новый образ получает последний описатель.
  - Поиск сервера: адреса из описателя → резервные места → экран «Сервер недоступен» с полем для ссылки.
  - Принимается только описатель с растущим `serial`.
- **Сервер потерян вместе с базой.** Ключи носителей восстанавливаются из контейнера администратора, пользователи заново активируются по коду.
- **Корневой ключ** — офлайн, подписывает только рабочие ключи и их отзыв. Закреплён на ESP и в образе.
- **Рабочий ключ** лежит в контейнере и подписывает выпуски и описатели.
- В программе — мастер «Корневой ключ».

## Носитель: службы

- **`poa-accessd`** — root, сокет, `SO_PEERCRED`. Только он владеет ключами и звеном и переключает стадии сетевого экрана. polkit разрешает только `start`/`stop` юнита `poa-vpn@<hex16>`.
- **Провайдеры VPN** с общим интерфейсом `prepare`/`up`/`is_connected`/`down`/`firewall_handoff`:
  - `openvpn` — делаем сейчас;
  - `vipnet` — клиент ставится шагом «Свои пакеты», каталог лежит в хранилище, пароль `.dst` приходит от нашего сервера, после подъёма туннеля фильтр ViPNet становится главным.
- **Сетевой экран (nftables)**, по умолчанию закрыт весь трафик:

  | Стадия | Что открыто |
  |---|---|
  | Нет сети | DHCP, DNS, проба и HTTPS к серверу |
  | Портал | веб только для cgroup окна портала, с тайм-аутом |
  | Сервер ответил | сервер и шлюз |
  | VPN поднят | туннель к целям |

  Входящее закрыто всегда.
- **Окно портала** — WebKitGTK под отдельным пользователем: без адресной строки, скачиваний, файловых диалогов и новых окон, хранилище в tmpfs. Закрывается само.
- **Токены на рабочем месте:**
  - пробрасывается только `/smartcard`, `/usb` запрещён;
  - подключаются только токены из белого списка VID:PID;
  - в образе нет PKCS#11 и утилит;
  - носитель-токен из проброса исключён;
  - вход по карте (`/smartcard-logon`) — отдельный этап.
- **Журнал событий:**
  - общий каталог `poa_events`;
  - очередь в разделе журналов, пачками на сервер, удаление после подтверждения;
  - сервер разворачивает коды в читаемые записи.

  Каталог событий — приложение В к [`THREAT-MODEL.md`](THREAT-MODEL.md).

### Журнал событий: правила (решение 01.10.2026)
- **Каталог согласован:** 11 групп на носителе (E, B, L, N, C, V, T, D, X, U, Y) плюс отдельный журнал сервера. Каждое событие ссылается на сценарий модели угроз. Каталог — приложение к `docs/THREAT-MODEL.md`.
- **До разблокировки LUKS в журнал не пишется ничего.** Отмечаются **вход** (E01) и **выход** (E02). Параметры входа:
  - способ и слот разблокировки (фраза, машинный слот, код восстановления);
  - хеш отпечатка машины;
  - число неудачных попыток с прошлого входа — из уже существующего счётчика лимита;
  - слот и `serial`;
  - причина отката слота — из `slot-state`;
  - признак нештатного прошлого выключения.

  Отдельных событий о неудачных попытках, о PIN токена и об отказах проверяющей ступени нет: эти данные приходят только параметрами входа.
- **Журнал на носителе не перезаписывается, пока его не принял сервер.** Кольцевого буфера нет. Сервер подтверждает приём до `seq`, только после этого носитель удаляет.

  Выгрузка идёт при каждом входе в сеанс, а сеанс без сервера невозможен, поэтому журнал копится только между сеансами. Если журнал всё же близок к заполнению (лавина событий — F3), информационные события перестают записываться, критические и высокие пишутся в резерв.
- **На сервере** коды разворачиваются в записи вида `ID_носителя: расшифровка кода`.
- **Стирание по отзыву на носителе не журналируется**: носитель затирается целиком. Факт фиксирует только журнал сервера — «отзыв доставлен носителю» с временем и адресом, в момент выдачи ответа «revoked». Событие Y01 из каталога носителя удалено.

## Обоснование решений

Вердикт: **О** — оставить, **П** — переработано, **У** — упразднено.

| Решение | Зачем | Вердикт |
|---|---|---|
| Корень в RAM | требование LiveCD; вредонос не переживает перезагрузку, на машине не остаётся следов | О |
| Слоты A/B | запись слота длится около 9 минут; без второго слота сбой питания в это время оставляет незагружаемый носитель | О |
| Проверяющая ступень и `kexec` | **токен:** только так обновлять ядро без администратора и проверять подпись до запуска. **Флешка:** защиты не даёт — ступень можно переписать; ценность в счётчике попыток без `save_env` grub и в едином пути с токеном (меньше кода, чем два загрузчика) | О, на флешке честно без пользы для безопасности |
| dm-verity | **токен:** целостность образа на RW-разделе. **Флешка:** дешёвые флешки портятся молча; verity превращает порчу в явную ошибку и откат на другой слот вместо странных падений | О |
| Образы без шифрования | секретов в них нет; ручное обновление не требует открывать LUKS | О |
| Отдельный раздел хранилища | звено, ключи и описатель должны пережить перезагрузку | О |
| Отдельный раздел журналов | лавина журналов не должна заполнить хранилище и сорвать запись звена — это была бы атака на доступность | О |
| Раздел обмена (флешка) | всё приходит по сети | **У** |

## Администраторы, ключи, запечатанный сервер, прочие меры модели угроз (Э21)

- **Носитель:** признак виртуализации (`systemd-detect-virt`, CPUID, DMI) уходит в запросе входа; сервер по политике группы отказывает в сеансе, флаг «разрешить ВМ» — для стенда.
- **Модель администраторов (решение 01.10.2026):**
  - **корень один на организацию**, лежит офлайн в сейфе;
  - **у каждого администратора свой рабочий ключ**, заверенный корнем;
  - носители и записи на сервере принадлежат **организации**, а не контейнеру (закрывает `PLAN.md:216`);
  - **добавить администратора** может только корень: он заверяет рабочий ключ, сервер создаёт слот при регистрации по одноразовому коду;
  - **удалить администратора** (слот распечатывания и рабочий ключ): при ≥3 администраторах — подписи двух **других** администраторов (двойной контроль), корень остаётся аварийным путём; при ≤2 — только корень;
  - последний слот администратора и аварийный слот корня удалить нельзя.
- **Ключ данных и слоты** (уточнение 01.10.2026, заменяет «один МК в контейнере»):
  - связку секретов шифрует один ключ данных (256 бит), в открытом виде он только в RAM;
  - на сервере лежат слоты — ключ данных, зашифрованный на личный ключ распечатывания каждого администратора (X25519, в его контейнере, выводится как в `config/exchange.py`). Слот 0 — аварийный, на корне;
  - **распечатывает любой зарегистрированный администратор** командой из программы;
  - **удаление администратора**:
    - контейнер уничтожен → слот удаляется и **меняется ключ данных**;
    - контейнер утерян → то же плюс мастер **смены секретов**: CA, ключи сервера с новым описателем, ключ семян TOTP. Иначе старая копия ВМ плюс утерянный контейнер раскроют действующий CA.
- **Сервер: «запечатанный сервер»** (решение 01.10.2026, вместо vTPM). Мастер-ключом служит **ключ данных** из слотов выше; сведения ниже — о его жизни на сервере.
  - **Связка секретов** (CA, ключи подписи и TLS, `tls-crypt-v2`, ключ семян TOTP, ключ паролей `.dst`) лежит на диске зашифрованной на ключ данных.
  - **Распечатывание:**
    - перезапущенный узел кластера получает ключ данных от живых узлов по взаимному TLS — только из кластерной сети, при действующей аренде в etcd и если узел был жив недавно; каждое такое распечатывание пишется событием;
    - холодный старт или одиночный сервер — подписанной командой «Распечатать» из программы администратора, удалённо;
    - TPM, если он есть, — необязательное автораспечатывание.
  - **Смена ключа данных** — из программы.
  - **Потеря всех контейнеров администраторов** — сервер распечатывается аварийным слотом корня. **Потеря и контейнеров, и корня** — новый CA и ключи сервера, новый описатель и повторная активация пользователей.
  - **Остаток:** снимок ВМ с памятью и консоль гипервизора — только организационные меры.
- Репликация PostgreSQL и etcd только по TLS. `install.sh` спрашивает имя физического хоста узла и предупреждает, если два узла кластера указали один хост: изнутри ВМ хост надёжно не определить, проверка декларативная. Резервные копии зашифрованы.
- Проверка звонящего при выдаче кодов восстановления — **ответственность администратора** (решение 01.10.2026). В модели угроз E2 закрывается организационной мерой оператора.
- **Токен:** реализации нет. Архитектура закладывается: поле `alg`, интерфейс подписанта (ключ из файла или PKCS#11), профиль `TOKEN`. Алгоритм (P-256 или ГОСТ) выбирается, когда появится экземпляр.
- **Шлюз:** роль `gateway` в `install.sh` плюс выгрузка «комплекта шлюза» (сертификат CA, серверный ключ `tls-crypt-v2` из запечатанной связки, образец `server.conf`, таймер CRL) — для компаний со своим шлюзом.

- **Образы — файлами на ext4, а не разделами A/B.** Выпуски весят по-разному (Debian 2,3 ГБ, РЕД ОС 4,5 ГБ): разделы фиксированного размера либо ограничили бы рост выпуска, либо тратили бы место. dm-verity над файлом через loop работает так же, как над разделом.
- **Корень проверяется dm-verity.** Дерево хешей — файл рядом с образом; корневой хеш — в `release.json` слота и в командной строке ядра (`poa.slot=`, `poa.roothash=`), с Э4 его передаёт проверяющая ступень после проверки подписи. Initramfs открывает образ через `veritysetup` и монтирует squashfs уже с `/dev/mapper`.
- **Активный слот** до Э4 выбирает `grub.cfg`, который пишется при записи и обновлении (без `save_env`); откат по счётчику попыток — в Э4.
- **Раздел обмена упразднён** (решение 01.10.2026). Файлы, которые администратор кладёт при записи (настройки программ), ложатся в слой носителя и при загрузке подключаются на прежний путь `/mnt/exchange` только для чтения, `noexec,nosuid,nodev` — пути в настройках программ не меняются. Записи пользователя туда больше нет.
- **Минимальный носитель — 16 ГБ**: служебные разделы 3 ГиБ, два образа РЕД ОС ≈ 9 ГБ.
- Носители разметки v2 обновляются только перезаписью.

## Э4: слоты A/B на GRUB (решение 02.10.2026, вместо проверяющей ступени)

Ступень на ESP + `kexec` отложена до токена: на флешке она безопасности не добавляет (её можно переписать), её ценность — RO-раздел токена; `kexec` под Secure Boot (lockdown) не проверить на стенде. Решение Максима — GRUB сейчас, ступень — вместе с токеном; формат выпуска общий.

- **Выпуск** `release.json`: номер (растёт), семейство, архитектура, разметка, sha256 ядра и initramfs, корневой хеш verity; подпись — рабочий ключ с сертификатом корня организации (`poa_trust`).
- **Выбор слота** — переменные GRUB на ESP (`poa_good`, `poa_try`, `poa_tries`): новый слот пробуется ограниченное число раз, затем GRUB сам возвращается к проверенному. Арифметики в GRUB нет — счётчик цепочкой сравнений.
- **«Загрузка удалась»** — служба после старта системы отмечает слот проверенным (`grub-editenv`) и поднимает `min_serial`.
- **Антиоткат** — initramfs сравнивает номер выпуска слота с `min_serial` в зашифрованном томе; ниже — не собирает корень.
- Минус, принятый сознательно: с токеном появится второй путь загрузки (ступень).

## Корень организации (решение 02.10.2026)

- **Два корня ГОСТ Р 34.10-2012** (`id-tc26-gost-3410-2012-256-paramSetA`): основной — на Рутокен ЭЦП 3.0 (ключ рождается и живёт в чипе), резервный — файл, зашифрованный сгенерированной фразой (33 знака, ≈192 бита; scrypt N=2^20, AES-256-GCM — симметричная часть стойка и к квантовому перебору). Подпись ГОСТ — не постквантовая (граница токена); алгоритм указан у каждого ключа, корень можно будет сменить без смены формата.
- **Якоря — не в образе**: образ подписан ключом администратора и не может нести собственный якорь. Якоря — в хранилище LUKS (`access.json` → `roots`), после замены — `/var/lib/poa/roots.json`; на ESP — с Э4.
- **Замена корня асимметрична** (уточнение после согласования): резервный заменяет основной, основной резервный — нет. Предложенное симметричное «заменяет другой» позволяло вору основного корня заменить резервный на свой и закрепиться навсегда — найдено тестом. Утерянный резервный восстанавливается перезаписью якорей носителя.
- **Сертификаты администраторов** — на рабочий ключ контейнера (Ed25519), на год; запрос → сверка отпечатка владельцем корня → подпись → установка только на собственный ключ контейнера. Отзыв рабочих ключей и замены корня едут с каждым описателем; носитель помнит самый свежий список отзыва.
- **ГОСТ на чистом Python** (`runtime/poa_gost.py`): в Python `cryptography` ГОСТа нет, в Debian 13 нет gost-engine. Константы «Стрибога» сгенерированы из текста RFC 6986; эталоны RFC 6986/7091 и сверка с OpenSSL gost-engine РЕД ОС в обе стороны. Это не сертифицированное СКЗИ.
- **Рутокен S** (подключён 02.10) — защищённое хранилище, не криптоустройство: подписывать на чипе не умеет, ключ копировался бы в память компьютера. Решение Максима — основной корень на ЭЦП 3.0.

## Э2: общий initramfs и «initrd носителя» (решение 02.10.2026)

**Задача.** Сейчас initramfs собирается при записи каждого носителя: в него вшиты имя тома (`poa-<id>`), UUID LUKS, ID носителя, crypttab, соль и запросы восстановления. Образ целиком (A/B, Э3b/Э4) так менять нельзя — initramfs должен быть один на выпуск и подписан.

**Решение — второй initrd.** Загрузчик (GRUB сейчас, `kexec` ступени в Э4) передаёт ядру два архива: общий initramfs выпуска и маленький `poa-medium.img` (cpio newc без сжатия) с тем, что своё у носителя:

| Путь в initramfs | Что |
|---|---|
| `/poa/env` | ID носителя, `POA_MAPPER`, UUID LUKS, слоты, параметры scrypt (как прежний `env`) |
| `/poa/recovery_salt.bin`, `/poa/requests` | данные модуля восстановления |
| `/cryptroot/crypttab` (Debian), `/etc/crypttab` (РЕД ОС) | строка корневого тома |

Ядро распаковывает архивы по очереди в один корень — штатный механизм (так грузят микрокод). Скрипты initramfs не узнают о носителе ничего при сборке: имя тома, UUID и ID берутся из `/poa/env`.

**Почему не монтирование ESP из initramfs:** нужны модули vfat/nls, ожидание устройства и выбор, какой из подключённых носителей «свой»; второй initrd этих вопросов не ставит. **Почему не командная строка ядра:** таблица запросов восстановления не помещается в 2 КБ.

**Безопасность.** `poa-medium.img` лежит рядом с initramfs на разделе загрузки — та же защита, что у initramfs сейчас (на флешке — обнаружение подмены по описи, Э5 — по подписи). Секретов в нём нет: соль и запросы и раньше лежали в незашифрованном initramfs.

**Порядок.** Общие файлы initramfs (хуки overlay, разблокировки, восстановления) и сам initramfs — в сборку дистрибутива; при записи — только `poa-medium.img` и строка `initrd … /poa-medium.img` в `grub.cfg`. Дистрибутивы, собранные раньше, записываются по-старому (признак в метаданных).
