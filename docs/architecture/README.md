# Архитектура системы «Якорь»

Срез кода `9d74f4d`, ветка `live-2.0`. Документация обновлена 15.11.2026.

Открой [редактируемый атлас draw.io](yakor-architecture.drawio) и выбери нужную вкладку. Компоненты называются по назначению; «сервер доступа» на схемах означает сервер доступа и управления.

Синий — механизм есть в коде; жёлтый — частичная интеграция; фиолетовый пунктир — целевой механизм; серый — внешний участник или пояснение. Наличие кода не подтверждает работу на стенде.

| Лист | Схема | Пояснение |
|---|---|---|
| 1 | 01 · Контекст системы «Якорь» | Удалённая работа остаётся на рабочем месте компании. Компоненты именуются по назначению. |
| 2 | 02 · Размещение и зоны доверия | Сервер доступа выдаёт допуск; пользовательский трафик идёт через VPN-шлюз, а не через HTTP-сервер сервера доступа. |
| 3 | 03 · Компоненты приложения администратора | Текущая ветка: Tkinter. Перенос на PySide6 находится в отдельной ветке и здесь не показан как готовый. |
| 4 | 04 · Компоненты сервера доступа и управления | API — интерфейс обмена программ. Секреты сейчас загружаются из файлов учётных данных службы. |
| 5 | 05 · Компоненты переносного устройства | Служба управляет сетью, обновлениями и событиями. Окно запрашивает действия через локальный сокет. |
| 6 | 06 · Данные и места хранения — сейчас | Ключи и полезная нагрузка схемы показаны по назначению; реальных секретов и адресов стенда здесь нет. |
| 7 | 07 · Ключи и цепочки доверия — сейчас | Основной ключ на токене не интегрирован. Рабочая подпись текущего контейнера — Ed25519; целевой ГОСТ показан отдельно. |
| 8 | 08 · Разделы носителя и загрузка | Образ ОС не лежит внутри LUKS. dm-verity проверяет блоки образа; текущая схема не гарантирует доверие к ядру до его запуска. |
| 9 | 09 · Сборка выпуска и выдача переносного устройства | Сборка образа и запись конкретного устройства — разные операции. Перезапись означает новую идентичность устройства. |
| 10 | 10 · Активация и вход на рабочее место | Схема успешного входа после активации. Отказы: нет TOTP, блокировка, старая версия, запрет ВМ, признак клона. |
| 11 | 11 · Удалённое восстановление доступа | Текущий код использует общий секрет контейнера. Индивидуальные секреты переносных устройств и перенос полномочий — целевая доработка. |
| 12 | 12 · Обновление A/B и возврат после сбоя | A/B — две области образа ОС. Успех подтверждается после проверки новой системы; антиоткат ограничивает допустимые версии. |
| 13 | 13 · Блокировка, отзыв и уничтожение | Блокировка и отзыв — разные действия. Серверное решение не означает, что отключённое устройство уже выполнила уничтожение. |
| 14 | 14 · Обмен конфигурациями — сейчас | Посылка переносит конфигурации. Передача записей переносных устройств, их секретов и серверного владения в этот протокол не входит. |
| 15 | 15 · Жизненный цикл устройства | Логическая модель сценариев. Это не перечень значений одного поля БД: локальная запись и серверное состояние различаются. |
| 16 | 16 · Серверные данные и связи | Логические связи по идентификаторам; схема не утверждает наличие внешних ключей SQL во всех таблицах. |
| 17 | 17 · Сетевой доступ по стадиям | Правила nftables дополняют ограничения киоска. DNS / DHCP / синхронизация времени относятся к базовой инфраструктуре. |
| 18 | 18 · Отказоустойчивость сервера доступа и управления | Кластерный вариант из сценариев развёртывания. Автопереключение адреса клиента не равно автоматическому поиску новых серверов. |
| 19 | 19 · Целевая модель администрирования | ЦЕЛЕВАЯ СХЕМА. Два токена — новое требование; копии полномочий не означают одинаковые неизвлекаемые ключи. |
| 20 | 20 · Переход от текущего к целевому | Схема разрывов реализации. Пунктир означает задачу разработки, а не уже работающий канал. |
| 21 | 21 · Завершение работы и границы ответственности | Закрыть окно RDP, отключить VPN и выйти из учётной записи рабочего места — разные действия. Единый сценарий требует доработки. |
| 22 | 22 · Угрозы, барьеры и пределы защиты | Архитектурная карта, не заключение аудита. Скомпрометированное железо хозяина остаётся существенной границей доверия. |

## Порядок чтения

Обзор 01–02; компоненты 03–05; данные и доверие 06–08; операции 09–15; данные, сеть и отказы 16–18; цель и разрывы 19–20; завершение и угрозы 21–22.

Исходные файлы указаны в подвале каждого листа. Модель БД показывает логические связи, а состояния устройства — сценарии, не значения одного поля. `../history/SOLUTION.drawio` сохранён как отдельная историческая модель целевого решения.

## Генерация и экспорт

`python3 tools/diagram/architecture_atlas.py` пересоздаёт атлас и эту инструкцию. Отдельные копии страниц и экспорты в репозитории не хранятся. Для экспорта нужен draw.io Desktop: `python3 tools/diagram/export_architecture.py /tmp/yakor-preview --format png`. Для одного листа добавь `--page 1`. SVG можно получить с `--format svg`.
