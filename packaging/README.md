# Упаковка (.deb / .rpm)

Собирает `portable-os-admin` в системный пакет для запуска прямо на
администраторской Linux-машине, без ручной установки Python-зависимостей.

**Ни `.deb`, ни `.rpm` не могут быть собраны или проверены из песочницы, в
которой разрабатывался этот проект (macOS без `dpkg-buildpackage`/`rpmbuild`)
— сборка и первый прогон должны выполняться на реальной Linux-машине**, тем
же порядком, что уже применяется для остального проекта (см. корневой
`README.md` / `docs/ARCHITECTURE.md`): собрать → сообщить об ошибках сборки
→ поправить.

## Почему Python-зависимости ставятся через venv, а не через системные пакеты

Проверено напрямую по `Packages.gz` реального Debian bookworm: пакет
`python3-textual` там есть, но версии **0.1.13** — это до полного переписывания
библиотеки, API несовместим с тем, что использует этот проект
(`textual>=0.58`, виджеты вроде `Switch`/`RichLog` в 0.1.13 либо отсутствуют,
либо работают иначе). Полагаться на системный пакет означало бы, что
приложение не запустится. `python3-cryptography` в bookworm (38.0.4) тоже
старее, чем зафиксировано в `pyproject.toml` (`>=41.0`), хотя используемые
здесь API (AES-GCM, scrypt) стабильны и, вероятно, работали бы — но полагаться
на не проверявшуюся версию не стоит.

Поэтому оба пакета (`.deb` и `.rpm`) при установке (`postinst`/`%post`):

1. создают приватный venv в `/opt/portable-os-admin/venv`
   (`python3 -m venv --system-site-packages`);
2. ставят туда сам `portable_os_admin` через `pip install
   /usr/share/portable-os-admin/app` — что тянет `textual`/`cryptography`
   нужных версий с PyPI.

`--system-site-packages` — не оговорка: GUI (`portable-os-admin`, теперь
интерфейс по умолчанию) собран на `tkinter`, который является C-расширением,
собранным вместе с системным Python, а не пакетом с PyPI — `pip install`
внутри изолированного venv никогда его не увидит. Поэтому `python3-tk`
(`.deb`)/`python3-tkinter` (`.rpm`) — обычные системные зависимости в
`Depends`/`Requires`, а не что-то, ставящееся через venv, и оба имени пакета
проверены напрямую по реальным индексам (`Packages.gz` Debian bookworm,
`primary.xml` RedOS 8.0), а не угаданы по конвенции именования RHEL/Debian.
Прежний TUI остаётся доступен как отдельная команда `portable-os-admin-tui`.

**Это требует доступа в интернет в момент установки пакета** (не только во
время `dnf --installroot`/`debootstrap` при самой установке ОС на носитель).
Пользователь подтвердил, что у тестовых машин (RedOS, доступ к RedOS/Astra/
BaseAlt зеркалам) есть полный доступ в сеть, так что это не блокирующее
ограничение здесь, но стоит иметь в виду при переносе на изолированную
машину.

## Почему `eatmydata` — в Recommends, а не в Depends

Установка ОС на флешку упирается не в сеть и не в процессор, а в то, что
`dpkg` вызывает `fsync()` после каждого распакованного файла. На реально
измеренном прогоне это разница между десятком минут и часом. Апстримный
`debootstrap` (проверено на Debian trixie) сам это не отключает — он
оставляет `/etc/dpkg/dpkg.cfg.d` пустым, — поэтому бэкенд Debian запускает
его через `eatmydata`, **если тот есть на машине администратора**, и
работает как раньше, если его нет. Отсюда `Recommends`, а не `Depends`:
ускоритель, а не требование. Пакеты, устанавливаемые уже после bootstrap,
ускоряются иначе — временным файлом `force-unsafe-io` в
`/etc/dpkg/dpkg.cfg.d` целевой системы, который удаляется до завершения
установки (тот же приём, что и у debian-installer).

## Известные ограничения

- **Кросс-семейная установка не покрыта пакетными зависимостями.** `.deb`
  тянет `debootstrap` (нужен для целей Debian/Astra) в `Depends`, но не
  умеет тянуть `dnf` для целей RedOS с Debian-хоста (это часть базовой
  системы RHEL-семейства, а не отдельный пакет, который можно поставить на
  Debian). Симметрично: `.rpm` не объявляет `debootstrap` в `Requires`,
  потому что при исследовании репозиториев RedOS (`repo1.red-soft.ru`) он
  там не был найден — если понадобится ставить Debian/Astra с RedOS-хоста,
  `debootstrap` придётся раздобыть отдельно (например, собрать из исходников
  или скачать `.deb` вручную и распаковать зависимости).
- **BaseAlt/Alt Linux как цель установки не поддерживается вообще** — не
  найдено подтверждённого способа bootstrap'а с чужого хоста (см.
  `docs/ARCHITECTURE.md` "Известные ограничения"), поэтому пакетные
  зависимости под него не добавлялись.
- Оба пакета помечены `Architecture: all`/`BuildArch: noarch`, так как сами
  по себе не содержат скомпилированного кода — единственная платформенная
  часть (`cryptography`'s C/Rust-расширения) разрешается `pip` в момент
  установки под конкретную машину.
- `postrm`/`%postun` удаляют venv только при полном удалении пакета
  (`purge`/удаление последнего экземпляра), не при обновлении.

## Сборка

```sh
# на Debian/Ubuntu/Astra Linux хосте
sudo apt-get install -y build-essential debhelper devscripts
./packaging/build-deb.sh

# на RedOS/RHEL-семейство хосте
sudo dnf install -y rpmdevtools rpm-build
./packaging/build-rpm.sh
```

## Структура

```
packaging/
  debian/          # каноничные файлы для dpkg-buildpackage (build-deb.sh
                    # копирует их во временный ./debian на время сборки)
                    # включая portable-os-admin.desktop (для GUI-лаунчера)
  rpm/
    portable-os-admin.spec   # генерирует .desktop-файл прямо в %install
  build-deb.sh
  build-rpm.sh
```
