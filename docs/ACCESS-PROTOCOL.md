# Протокол сервера доступа v3

Договор между тремя сторонами: сервером доступа (этап Э6), программой
администратора (Э7) и клиентом сеанса на носителе (Э8). Устройство решения и
причины — [`LIVE-2.0.md`](LIVE-2.0.md), угрозы — [`THREAT-MODEL.md`](THREAT-MODEL.md).
Состояние носителя перед входом проверяет подписанный запрос к `/v3/media-state`.
[Протокол отзыва](REVOCATION-SERVER.md)

Статус: **черновик договора, 01.10.2026.** Меняется вместе с реализацией; каждое
изменение — в этом файле тем же коммитом.

## 1. Ключи

| Ключ | Алгоритм | Где закрытая часть | Для чего |
|---|---|---|---|
| Корневой ключ организации | Ed25519 | офлайн, сейф | заверяет рабочие ключи администраторов и их отзыв; аварийный слот распечатывания |
| Рабочий ключ администратора | Ed25519 | контейнер администратора | подписывает выпуски образа, описатели сервера, команды серверу (бывший «ключ полномочий») |
| Ключ распечатывания администратора | X25519 | контейнер администратора | слот ключа данных сервера |
| Ключ подписи сервера | Ed25519 | запечатанная связка сервера | подписывает состояние носителя (бывший «ключ отзыва» — открытая часть уже на носителях) и выдачи доступа v3 |
| TLS-ключ сервера | P-256 | диск сервера (nginx) | транспорт; закреплён в описателе по SPKI |
| Ключ CA для VPN | ECDSA P-256 | запечатанная связка | сертификаты клиентов OpenVPN на 24 ч, CRL |
| Серверный ключ `tls-crypt-v2` | формат OpenVPN | запечатанная связка (и шлюз) | клиентские ключи `tls-crypt-v2` на сеанс |
| Ключ семян TOTP | AES-256-GCM | запечатанная связка | шифрует семена TOTP в базе |
| Ключ паролей `.dst` | AES-256-GCM | запечатанная связка | шифрует пароли дистрибутивов ключей ViPNet в базе |
| Ключ носителя | Ed25519 (флешка); P-256 или ГОСТ (токен, позже) | хранилище носителя / чип | подпись запросов носителя |

**Почему ответы подписываются поверх TLS.** TLS-ключ nginx лежит на диске сервера
и уходит вместе с копией ВМ (сценарий V1). Сам по себе он позволил бы выдать себя
за сервер и подсунуть ложные цели — то есть выманить пароль рабочего места.
Выдачи доступа и описатели поэтому подписаны ключами, которых на диске в открытом
виде нет: ключом подписи сервера из запечатанной связки и рабочим ключом
администратора.

## 2. Транспорт

- Только HTTPS, TLS 1.3. Публичные удостоверяющие центры не участвуют: клиент
  сверяет SHA-256 от SubjectPublicKeyInfo сертификата сервера с одним из
  отпечатков `tls_spki` в описателе и обрывает соединение при несовпадении
  **до отправки чего-либо** (событие C03).
- Тела запросов и ответов — JSON в UTF-8, `Content-Type: application/json`,
  `Cache-Control: no-store`. Размер тела запроса — не больше 64 КиБ, кроме
  `/v3/events` (256 КиБ).
- Каждый ответ v3 содержит `server_time` (UTC, секунды). Клиент поправляет по нему
  часы до запуска VPN (событие E05).

## 3. Аутентификация носителя

1. `POST /v3/nonce` с телом `{"media": "<id>"}` → `{"nonce": "<32 hex>", "ttl": 120}`.
   Без подписи: nonce ничего не открывает, а неизвестному носителю выдаётся так
   же, чтобы ответ не подсказывал, какие носители существуют.
2. Каждый следующий запрос несёт заголовки:

   ```
   X-POA-Media: <id>
   X-POA-Nonce: <nonce из шага 1>
   X-POA-Signature: <base64 подписи>
   ```

   Подписывается строка (байты UTF-8, без завершающего перевода строки):

   ```
   poa-v3
   <МЕТОД> <путь>
   <id>
   <nonce>
   <sha256 тела, hex>
   ```

   Алгоритм проверки — тот, что записан за носителем при регистрации; поле
   алгоритма в запросе не передаётся, понижать нечего.
3. Nonce одноразовый, живёт 120 с и гасится **в той же транзакции**, что и
   изменение звена и `last_step` TOTP (раздел 6).
4. Любая неудача на этом уровне — `403` с одним и тем же телом
   `{"error": "forbidden"}`.

## 4. Описатель сервера

`GET /v3/descriptor` — без аутентификации. Тот же файл лежит в резервных местах
поиска и в каждом выпуске образа.

```json
{
  "descriptor": {
    "format": 1,
    "serial": 7,
    "org": "<отпечаток корневого ключа, 16 hex>",
    "endpoints": ["https://a.access.example.org", "https://b.access.example.org"],
    "tls_spki": ["<sha256 hex>", "<sha256 hex следующего ключа>"],
    "server_sign_keys": ["<base64 Ed25519>"],
    "revoked_server_keys": ["<base64 Ed25519>"],
    "fallback": ["https://www.example.org/poa/descriptor.json"],
    "issued_at": 1790000000
  },
  "signature": "<base64 подписи канонического JSON поля descriptor рабочим ключом>",
  "signer": {
    "key": "<base64 рабочего ключа>",
    "cert": "<base64 подписи корнем строки 'poa-admin-key <key> <not_after>'>",
    "not_after": 1830000000
  }
}
```

**Канонический JSON** здесь и далее: `json.dumps(obj, ensure_ascii=False,
sort_keys=True, separators=(",", ":"))`, затем UTF-8.

Носитель принимает описатель, если (1) подпись верна, (2) рабочий ключ заверен
корнем, закреплённым в образе, и не отозван, (3) `serial` больше сохранённого.

## 5. Активация

`POST /v3/activate` (аутентифицирован, раздел 3):

```json
{"code": "XXXXX-XXXXX", "info": {"version": "2.0.0", "machine": "<8 hex>", "virt": "none"}}
```

- Код — 10 знаков base32 (50 бит), одноразовый, живёт 72 часа; на сервере хранится
  только SHA-256 кода.
- Ответ `200`:

  ```json
  {"grant": {"totp": {"secret": "<base32>", "digits": 6, "period": 30, "algorithm": "SHA1"},
             "link": "<base64 32 байт L0>", "server_time": 1790000000},
   "signature": "<base64 подписи канонического grant ключом подписи сервера>"}
  ```

- Активация считается состоявшейся после первого успешного
  `/v3/session/confirm`. До этого повторный запрос с тем же кодом от **того же**
  носителя выдаёт новое семя и новое L0 (пользователь мог не дойти до QR).
- Код уже использован другим носителем или активация уже состоялась —
  `409 {"error": "already_activated"}`, событие сервера, носитель блокируется,
  если он чужой. Истёкший код — `410`.

## 6. Вход

### 6.1. `POST /v3/session`

```json
{"totp": "123456", "link": "<base64 N>",
 "status": {"slot": "A", "serial": 41, "distribution": "<id>", "virt": "none",
            "machine": "<8 hex>", "medium": "flash"}}
```

Сервер **в одной транзакции** с блокировкой строки носителя:

1. гасит nonce;
2. проверяет, что носитель не заблокирован (`423`) и не отозван (`403`);
3. проверяет политику ВМ группы (`403 {"error": "virtualization"}`);
4. проверяет TOTP: RFC 6238, окно ±1 шаг, шаг строго больше `last_step` (`401`);
5. применяет правила звена (6.3);
6. проверяет `min_serial` (`426 {"error": "update_required", "release": {...}}`).

Ответ `200`:

```json
{"proposal": "<base64 N+1>",
 "release": {"distribution": "<id>", "serial": 42, "min_serial": 40,
             "url": "/v3/release/<id>/42/", "files": ["release.json", "release.sig", "..."]},
 "server_time": 1790000000}
```

Доступа ещё нет.

### 6.2. Подтверждение входа и выбор места

После сохранения нового звена USB отправляет `POST /v3/session/confirm` с полями
`link` и `nonce`. Этот nonce — 16 случайных байт в виде 32 строчных hex-цифр,
сгенерированных носителем для проверки ответа. Заголовок `X-POA-Nonce` из
раздела 3 по-прежнему связывает запрос с одноразовым вызовом сервера.

Сервер фиксирует звено и возвращает подписанный каталог. В `grant` входят
`purpose=catalog`, `media`, клиентский `nonce`, случайный идентификатор `session`,
`server_time`, `not_after` и `targets`. Срок MFA отмеряется от проверки TOTP и
в текущем стендовом профиле составляет восемь часов. В каждом элементе каталога
есть `id`, `name`, числовая `version` и `revision` (SHA-256 канонического JSON
с версией, полным профилем цели и описанием её транспорта). Открытие каталога
оставляет рабочую сеть закрытой. Сохранённые ранее SSH-назначения исключены
из обоих каталогов. Сервер отклоняет попытку создать или выбрать SSH-назначение.

Все следующие команды — подписанные POST-запросы носителя к `/v3/session/<команда>`.
Каждый запрос содержит `session` и свежий клиентский `nonce`. Сервер проверяет
носитель, отзыв, блокировку, номер записи парка, срок MFA, политику запуска и
минимальный выпуск в одной транзакции с изменением сеанса.

| Команда | Дополнительные поля запроса | Подписанный результат |
|---|---|---|
| `catalog` | — | Актуальный список мест. |
| `select` | `generation`, `target_id`, `revision`, `vpn` с открытым ключом клиента OpenVPN | Профиль одной цели `target`, её транспорт `vpn`, актуальный каталог и срок допуска. |
| `renew` | `generation`, `target_id`, `revision` | Подтверждение действующего выбора и новый предельный срок. В ответе также передаётся актуальный каталог. |
| `release` | `generation` | Подтверждение закрытия текущего выбора, актуальный каталог. Действующий сеанс MFA допускает следующий выбор. |

Носитель проверяет подпись канонического `grant`, назначение ответа `purpose`,
носитель, сеанс и свой одноразовый запрос. При выборе и продлении проверяются
также поколение выбора, идентификатор и точная ревизия. При выборе носитель
пересчитывает хеш по полученной цели и параметрам транспорта. Новое поколение
строго больше предыдущего в том же сеансе MFA. Замена активного профиля,
возврат параметров после удаления цели и изменение транспорта инвалидируют
прежний допуск. При продлении изменения остальных целей обновляют каталог.

Допуск действует до меньшего из конца MFA и 300 секунд от запроса. Носитель
отсчитывает подписанную разность `not_after - server_time` от момента отправки по
часам Linux `CLOCK_BOOTTIME`, которые учитывают сон. Запоздалый ответ отклоняется.
После истечения рабочего допуска требуется новый вход с MFA. При старом формате
`confirm` рабочие реквизиты не выдаются.

**Граница прототипа.** В этом переходе адаптер первого стенда выдаёт клиентский
сертификат его OpenVPN только по `select`. Срок сетевого допуска проверяется
отдельно от срока сертификата. Целевая схема использует зашифрованный пакет
владельца и внешние реквизиты организации. Для неё ещё требуются подпись
владельца на пакете и отдельный заверенный ключ допуска каждого узла. Текущий
профиль использует существующий серверный ключ подписи v3.

### 6.3. Правила звена

C — подтверждённое звено, P — предложенное, история — SHA-256 всех когда-либо
выданных звеньев носителя. Сервер хранит только хеши.

| Предъявлено в `/v3/session` | Реакция |
|---|---|
| v = C, P нет | создать P, ответ 200 |
| v = C, P есть | старое P в историю, новое P, событие «аномалия» |
| v = P | засчитать как подтверждение (C = P), создать новое P |
| v в истории | **клон**: блок носителя, все действующие сертификаты носителя в CRL, событие, `409 {"error": "clone"}` |
| иначе | `403` |

| Предъявлено в `/v3/session/confirm` | Реакция |
|---|---|
| v = P | C = P, N в историю, выдать подписанный каталог |
| иначе | `403` |

### 6.4. Коды ответов

| Код | Тело | Когда |
|---|---|---|
| 200 | см. выше | успех |
| 401 | `{"error": "totp"}` | неверный или повторный код TOTP |
| 403 | `{"error": "forbidden"}` | любая неудача аутентификации, отзыв, неизвестное звено |
| 403 | `{"error": "virtualization"}` | запуск в ВМ запрещён политикой группы |
| 409 | `{"error": "clone"}` / `{"error": "already_activated"}` | раздел 5 и 6.3 |
| 401 | `{"error": "session_expired"}` | истёк срок MFA или выбранного места |
| 409 | `{"error": "assignment_changed"}` / `{"error": "selection_changed"}` | версия назначения или поколение выбора уже изменились |
| 410 | `{"error": "expired"}` | код активации истёк |
| 423 | `{"error": "blocked"}` | носитель заблокирован |
| 426 | `{"error": "update_required", "release": {...}}` | `serial < min_serial` |
| 429 | `{"error": "rate"}` | слишком часто |

## 7. Журнал событий

`POST /v3/events` (аутентифицирован):

```json
{"catalog": 1, "events": [{"seq": 101, "code": "E01", "t": 1790000000,
                           "boot": "<boot_id>", "p": {"slot": "A", "fails": 0}}]}
```

Ответ — `{"acked": 101}`: наибольший `seq`, до которого сервер принял всё без
пропусков. Носитель удаляет подтверждённое. Пропуск номеров сервер записывает
событием «потеряна часть журнала» (F1). Каталог кодов — приложение В к
[`THREAT-MODEL.md`](THREAT-MODEL.md).

## 8. Для шлюза и для всех

- `GET /v3/crl` — CRL в PEM, без аутентификации. Шлюз забирает раз в минуту.
- `GET /v3/release/<distribution>/<serial>/<файл>` — файлы выпуска, без
  аутентификации, с поддержкой `Range`. Подлинность — подписью `release.json`.

## 9. Команды администратора

`POST /admin/v3/<команда>`, тело — канонический JSON с полями `cmd`, `counter`
(строго возрастает у каждого администратора) и параметрами команды. Заголовки
`X-POA-Key-Id` (отпечаток рабочего ключа) и `X-POA-Signature` (подпись тела).
Перечень команд (активация, цели, группы и назначения, выпуски, `min_serial`,
разблокировка, события, администраторы, распечатывание) уточняется в этапе Э7 и
дописывается сюда.

## 10. Хранение на сервере (логически)

| Таблица | Что |
|---|---|
| `media` | носитель: владелец-организация, группа, ключ носителя и алгоритм, состояние, блокировка, последняя связь |
| `access` | семя TOTP (зашифровано), `last_step`, хеши C и P, признак активации |
| `link_history` | хеши выданных звеньев |
| `activations` | хеш кода, носитель, срок, использован ли |
| `nonces` | nonce, носитель, срок |
| `certs` | серийные номера выданных сертификатов, срок, отозван ли |
| `targets`, `target_versions` | профили по носителям и номера версий, сохраняемые после удаления цели |
| `employee_sessions` | состояние MFA, выбранная цель, поколение, ревизия и предельный срок |
| `groups`, `assignments`, `distributions`, `releases` | управление выпусками |
| `events` | журнал носителей (принятые коды) и журнал сервера |

В Э6 реализуется поверх sqlite (как v2), в Э17 — на PostgreSQL за тем же
интерфейсом хранилища.
