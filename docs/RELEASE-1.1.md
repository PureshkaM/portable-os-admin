# Выпуск 1.1.0

Файл ведётся с 15.09.2026 и живёт до выхода 1.1.0. Соседние документы:
[`../README.md`](../README.md) — о проекте, [`PLAN.md`](PLAN.md) — общий список
задач, [`REVOCATION-SERVER.md`](REVOCATION-SERVER.md) — сервер отзыва.

## Цель и границы

Первая полностью работающая версия решения вместе с серверной частью:
приложение, носитель и сервер отзыва, выпущенные одним релизом.

**Входит:**

1. Отзыв v2: носитель доказывает серверу, что он настоящий; постороннему
   запросу — 403. Опрос раз в 5 минут и при подъёме сети.
2. Шлюз сеанса: пока сервер в этом сеансе не ответил подписанным «ok»,
   запускаются только настройки сети. Нет связи — системное уведомление.
3. Сервер: протокол v2, учёт последней связи, гонка при знакомстве, 500 на
   нечисловом `Content-Length`.
4. Долги: подпись дистрибутива, браузер пакетов из образа, режим «подробная
   загрузка».
5. Документация: устаревшие комментарии, честная модель угроз для привязки и
   отзыва.
6. Задача 24 (список окон на панели Debian + MATE).
7. Живые прогоны на файл-образе: новый порядок уничтожения, `systemd-cryptsetup`
   на Debian 13, шлюз сеанса.
8. Выпуск: версия 1.1.0, тег, GitHub Release с `.deb`, `.rpm` и архивом
   сервера.

**Не входит:** dm-verity (см. «Решения»), флешка и `.rpm` на настоящей РЕД ОС —
ресурсов нет, в CHANGELOG помечаются непроверенными.

## Протокол отзыва v2

### Ключи

| Ключ | Закрытая часть | Открытая часть | Зачем |
|---|---|---|---|
| Отзыв (сервер) | только на сервере | в контейнере и на каждом носителе | подпись ответов носителям |
| Полномочия администратора | выводится из семени контейнера | на сервере в `admins/` | подпись команд серверу |
| **Ключ носителя (новый)** | только на носителе, `/etc/poa/device.key`, 0400 root, на зашифрованном корне | в записи носителя в контейнере и на сервере | подпись запросов носителя |

Ключ носителя — Ed25519, рождается при записи носителя (оба пути, общий
помощник `_write_medium_files`). В контейнере хранится только открытая часть:
закрытой незачем покидать носитель. Пользователь киоска прочитать файл не
может — root и 0400.

### Выпуск носителя: администратор → сервер

```
POST /admin/media/<id>
X-POA-Key-Id: <отпечаток ключа полномочий>
X-POA-Signature: <подпись тела>

poa-media <id> <номер> <ok|revoked> <ключ носителя: base64 сырых 32 байт>
```

Правила прежние (владелец, возрастающий номер). Ключ носителя обязателен:
запись без него сервер не заводит (400). Владелец может заменить ключ
следующей командой — это перевыпуск носителя с тем же идентификатором.

### Носитель спрашивает

```
GET /v2/state
X-POA-Media: <id: «приставка-носитель», 8+8 hex; до 1.1.0 — 8 hex>
X-POA-Nonce: <32 hex>
X-POA-Info: version=<версия>;machine=<8 hex отпечатка машины>
X-POA-Signature: <base64 подписи ключом носителя>
```

Подписывается строка `poa-ask <id> <nonce> <info>` без перевода строки.
Всё в заголовках, а не в адресе: в журнал nginx адрес попадает, заголовки —
нет, и по адресу в браузере запрос не повторить.

Ответ `200`, `text/plain`:

```
poa-state <id> <nonce> <ok|revoked>
<base64 подписи первой строки ключом отзыва>
```

**Всё прочее — `403` с одинаковым телом:** нет заголовков, неизвестный
носитель, у записи нет ключа, подпись не сходится, случайное число уже
встречалось, разбор не удался. Одинаковый ответ не подсказывает перебирающему,
на каком шаге он споткнулся. Обычный человек, открывший путь в браузере,
получает 403.

Повтор перехваченного запроса закрыт памятью сервера: случайные числа
носителя хранятся 7 дней, повтор — 403. Без этого переигранный запрос
отмечал бы в учёте живым носитель, который давно не включался.

Сервер при успешном запросе запоминает время, версию и отпечаток машины —
это учёт парка.

`GET /state` (протокол 1.0.0) удаляется и отвечает 403: носителей 1.0.0 в
работе нет, только стендовые.

### Администратор спрашивает о носителе

```
GET /admin/media/<id>
X-POA-Key-Id: <отпечаток>
X-POA-Time: <unix-время>
X-POA-Signature: <подпись строки "poa-query <id> <время>">
```

Окно времени ±300 с — часам машины администратора доверять можно, в отличие
от переносного носителя. Ответ `200`:
`poa-record <id> <состояние> <последняя связь ISO|-> <версия|-> <машина|->`.
Не владелец — 403.

### Носитель поступает

* подпись ответа сошлась и число наше, `ok` → `/run/poa/authorized` с текущим
  `boot_id`, шлюз открыт;
* то же, `revoked` → уничтожение (порядок 1.0.0);
* всё прочее → уведомление «нет связи с сервером авторизации»; шлюз остаётся
  таким, каким был (закрыт до первого `ok`, открыт после).

## Решения

| Решение | Почему |
|---|---|
| Сервер решает, носитель проверяет подпись ответа | Уничтожение необратимо; без подписи его вызовет любой, кто подменит ответ по дороге. Проверка подлинности — не обработка |
| Ключ носителя, а не общий секрет | Взлом сервера не даёт выдать себя за носители; закрытая часть в одном месте |
| Неизвестный носитель — 403, а не «ok» | Смена решения 1.0.0. Раньше неизвестность не мешала работать; теперь «ok» открывает сеанс, и его нельзя выдавать тому, кого сервер не знает. Следствие: носитель должен быть опубликован на сервере при выпуске, иначе сеанс не откроется |
| Опрос 5 минут + диспетчер NetworkManager | Wi-Fi, подключённый в сеансе, проверяется сразу, а не через 5 минут |
| После «ok» потеря связи ничего не закрывает | Решение пользователя: обрыв Wi-Fi в дороге не должен отбирать VPN; предупреждение уведомлением |
| Шлюз только в режиме киоска | В консольном режиме запускать через `.desktop` нечего |
| ID носителя — «приставка администратора-носитель» | Восьми знаков хватало, пока сервер был свой у каждого; на общем сервере записи всех администраторов в одной таблице. Приставка — отпечаток **открытой** части ключа администратора: секрет в вычислении не участвует, обратного хода нет. В код восстановления приставка не едет — контейнер, читающий код, её знает, — но сам код выводится от полного ID, которым записан keyslot |
| Уничтожение глушит сигналы и уходит из корневой cgroup | Живьём дважды убито снаружи сигналом 6 на середине затирания: ключи, загрузчик и разметка уничтожены, данные затёрты наполовину, носитель не выключился. Отправитель не найден, поэтому защита не от него, а от любого: игнор переживает `exec` и достаётся dd, выход из cgroup уводит из-под группового убийства. От SIGKILL по конкретному PID не спасает |
| dm-verity отложен | Корневой хеш проверяет initramfs с открытого `/boot`; подменивший initramfs подменит и проверку. Хранение эталона в зашифрованном разделе круга не размыкает: сверку выполняет тот же непроверенный код. Размыкает только измерение до исполнения (Secure Boot, TPM) |
